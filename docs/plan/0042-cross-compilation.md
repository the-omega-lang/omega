# Cross-Compilation and AVR Target Support

## Task Description
- **Deliverable:** make `omgc --target=<target>` a reliable cross-compilation path that emits object/IR/assembly for a non-host target, with the requested acceptance targets `aarch64-linux`, `x86_64-windows`, and `avr-none`. `avr-none` becomes a first-class shared target with 16-bit pointers. Completion for this task means the compiler emits a valid object of the requested architecture/object format and the emitted LLVM target metadata agrees with the requested Omega target.
- **Purpose:** finish the target plumbing Omega has already been designed around instead of adding a parallel cross-compilation mechanism. The same target must continue to drive semantic width/layout decisions and LLVM emission so freestanding/embedded targets are not a backend-only afterthought.
- **Chosen direction:**
  - Keep the existing `omega_analyzer::Target { arch, os }` as the single compiler-wide target vocabulary and keep `--target` as the explicit CLI selection. The flag already parses and propagates through `Driver`, MIR lowering, and `CodegenRequest`; this task completes/hardens that path rather than introducing another target abstraction.
  - Add `Arch::Avr` with a 2-byte/16-bit pointer width. Treat `avr-none` as generic AVR for now; LLVM's generic AVR CPU baseline is sufficient for object generation. MCU/feature selection is a later extension.
  - Make every pointer-sized semantic/codegen operation genuinely width-generic for the supported 16/32/64-bit widths. In particular, `usize`/`isize`, `sizeof`, GEP/index offsets, pointer arithmetic/casts, and vtable/spec offsets must not use a 32-vs-64 shortcut.
  - Preserve the semantic distinction between a data pointer and a function value in the backend-neutral leaf sequence (both remain one pointer-width leaf) so LLVM can map function-pointer leaves to its program address space on Harvard targets. On AVR, functions/code pointers use LLVM's program address space while ordinary data pointers remain address space 0; raw-pointer <-> function-pointer reinterpret casts become LLVM address-space casts only when the source/destination spaces differ.
  - Let LLVM target-machine construction be the authority for whether the compiler build can emit the selected target. Remove the current unconditional `llvm::supports` stub rather than adding a duplicated hard-coded support matrix. Backend setup must fail before module emission with a normal compiler error if LLVM cannot construct the requested target.
  - Preserve the existing documented omitted-target behavior (`Target::DEFAULT == x86_64-unknown-linux`). Host autodetection is not part of this task.
- **Rejected alternatives:**
  - Do not accept arbitrary raw LLVM triples in `omgc`; that would leak backend vocabulary into semantic analysis and allow analyzer/codegen target facts to diverge.
  - Do not add a libc/musl/MSVC/platform-runtime component to the target string. Runtime/platform selection remains a linkage/package concern; this task is architecture/OS object emission.
  - Do not call AVR supported merely because a trivial empty module emits. AVR's LLVM code/data address-space distinction must be handled for Omega function values, indirect calls, and vtables so the target is not knowingly partial at a core pointer representation boundary.
  - Do not build QEMU/emulator/remote execution infrastructure here. Cross-target execution testing is the separate structural task requested by the user.

## Technical Details
- **Initial context boundary:**
  - Shared target/width semantics: `compiler/omega-analyzer/src/target.rs`, `resolved_type.rs`, `layout.rs`, plus `docs/language/types-and-primitives.md` and `docs/architecture/types-layout-and-const-eval.md`.
  - Native target setup/emission: `compiler/omega-codegen/src/{lib.rs,abi.rs}` and `compiler/omega-codegen/src/llvm/{mod.rs,leaf.rs,expr.rs,place.rs,function.rs,vtable.rs,inline_asm.rs}`, guided by `docs/architecture/mir-and-codegen.md` and `docs/architecture/abi-and-representation.md`.
  - CLI surface: `compiler/omgc/src/{cli.rs,app.rs}` and `docs/guide/compiler-cli.md`. `app.rs` already passes one `Target` to `Driver::new`, `Driver::compile`, and `CodegenRequest`; preserve that contract.
  - Test-layer guidance: `docs/architecture/testing-and-validation.md`. Root `tests/` currently link and execute host objects, so they are not the place to invent the deferred cross-target execution harness.
- **Affected files/symbols:**
  - `omega-analyzer/src/target.rs`: add `Arch::Avr`; parse/display `avr`; return `pointer_bytes() == 2`; include AVR in supported-architecture diagnostics/tests. Keep the two-/three-segment Omega target syntax and fixed default unchanged.
  - `ResolvedType::integer_domain`: handle 16-bit `ISize`/`USize` explicitly instead of treating every non-32-bit target as 64-bit. Add focused tests in the existing `resolved_type/tests.rs` module.
  - `omega_analyzer::layout::Leaf` / `leaves_of`: distinguish function/code-pointer leaves from ordinary data-pointer leaves while keeping both `Leaf::bytes(pointer_bytes) == pointer_bytes` and the same one-leaf ABI shape. This is representation metadata for codegen, not a new source-language pointer kind.
  - `omega-codegen/src/llvm/leaf.rs`: make leaf-to-LLVM-type mapping target-aware. Keep ordinary pointers in address space 0; map the function-pointer leaf to the target program address space (`1` for AVR, default `0` for current Von Neumann targets). Reuse one `size_type` mapping for 16/32/64-bit pointer-sized integers.
  - `omega-codegen/src/llvm/{expr.rs,place.rs}`: remove every `pointer_bytes() == 8 ? i64 : i32` construction and use the shared pointer-sized integer helper. This includes `MirExpr::Sizeof`, array/slice indexing, byte GEPs, spec/vtable offsets, and aligned pointer loads. Pointer reinterpret/int-to-pointer helpers must use the *requested LLVM pointer type* rather than always `Codegen::ptr_type`; when both sides are pointers with different LLVM address spaces, emit `build_address_space_cast`.
  - `omega-codegen/src/llvm/{function.rs,vtable.rs}`: function signatures containing function values must consume the function-pointer leaf type; vtable entries are code pointers, while the vtable object itself remains an ordinary data pointer. Dynamic dispatch must load a code pointer before `build_indirect_call`. Direct function declarations continue to be created after the module triple/data layout is installed so LLVM places functions in the target's program address space.
  - `omega-codegen/src/llvm/mod.rs`: add AVR triple mapping. For `avr-none`, use LLVM's canonical generic AVR triple (`avr-unknown-unknown`) rather than assuming the generic hosted/freestanding string builder is correct for this backend. Keep target-machine CPU/features generic; use LLVM's default relocation mode for AVR instead of forcing PIC, while preserving current relocation behavior for the already-working targets. Remove/replace the fake `supports` contract so `Target::from_triple` / `create_target_machine` setup is the single support decision and produces the existing user-facing unsupported-target error before emission.
  - `omega-codegen/src/llvm/inline_asm.rs`: make `Arch::Avr` exhaustive. AVR uses LLVM's non-x86 dialect and generic `r` class; LLVM only has concrete `r` register classes for target-representable operand widths, so unsupported user `reg(...)` shapes may continue to surface as normal object/assembly-emission errors under the existing inline-asm contract. AVR has no extra status-clobber list here.
  - `compiler/omgc/src/cli.rs`: no new flag plumbing is needed; add explicit parsing coverage for the three requested target spellings and keep invalid target diagnostics. Update help text only as needed to show the shorter `<arch>-<os>` form the user will normally type.
  - Docs: update `docs/guide/compiler-cli.md` with the supported spellings/examples and generic-AVR meaning; update the target/leaf/address-space invariants in `docs/architecture/{types-layout-and-const-eval.md,abi-and-representation.md,mir-and-codegen.md}`. `docs/language/types-and-primitives.md` already specifies that `usize`/`isize` use target pointer width, so do not invent a new language rule there.
- **Interfaces/invariants:**
  - One `omega_analyzer::Target` chosen by CLI must reach semantic analysis and LLVM unchanged; no phase may fall back to host width/triple.
  - `usize`/`isize` width, pointer leaf byte size, LLVM pointer-sized integer type, and target-machine data layout must agree for every supported target.
  - Function values and raw data pointers remain the same Omega size/leaf count and remain explicitly castable as specified today; LLVM address-space casts are backend representation work, not an ABI adapter or source-visible conversion.
  - Cross-compilation is host-independent: never reject a target just because it differs from the machine running `omgc`.
  - `Os::None` remains freestanding: no libc, CRT, linker, sysroot, or runtime object is implicitly introduced by selecting `avr-none`.
  - Object emission remains separate compilation only. The compiler writes the object bytes; it does not invoke a host/cross linker in this task.
- **Out of scope:** QEMU/emulator execution, a cross-target test farm, linker/sysroot/toolchain discovery, automatically building `core`/`std`/`plat` for each target, target-specific runtime glue, Arduino board support, AVR MCU selection (`atmega328p`, etc.), CPU feature flags, changing the target-string model to include libc/environment, host-target autodetection, and proving runtime correctness on foreign hardware.
- **Risks/open questions:** no product/design decision is left to the implementer. If LLVM 21.1 in the repository's actual build cannot create or emit the generic AVR target despite the registered backend, stop and report that toolchain/build limitation rather than silently degrading `avr-none` into a partial/unchecked target. Likewise, if a remaining data-vs-code pointer path appears that cannot be represented with the settled leaf distinction/address-space-cast model, stop rather than collapsing all AVR pointers back to address space 0.

## Implementation Plan
1. **Add AVR to the shared target vocabulary and make 16-bit semantics correct.** Extend `Arch`, `Target::parse`, `Display`, pointer-width tables, and target parser tests in `target.rs`. Fix `ResolvedType::integer_domain` for 16/32/64-bit `isize`/`usize` and add explicit 16-bit range tests so analyzer literals/patterns/const evaluation cannot silently use 64-bit domains on AVR.
2. **Represent code pointers distinctly without changing Omega pointer size/ABI shape.** Add a function-pointer/code-pointer `Leaf` variant in `layout.rs`; map `ResolvedType::Function(_)` to it while raw pointers/arrays/slices/spec metadata keep ordinary pointer leaves. Update leaf-size/layout/ABI unit expectations as needed, preserving one pointer-width leaf in every case.
3. **Centralize target-aware LLVM scalar/pointer types.** Refactor `llvm/leaf.rs` so `llvm_type`/`llvm_leaves` receive the active target (or an equivalent single target-aware backend context), map pointer-sized integers through one 16/32/64 helper, and map code pointers to AVR's program address space. Add a small codegen helper for the function-pointer LLVM type so vtable/call code never recreates the address-space rule.
4. **Remove 32/64-only backend assumptions.** Replace the six current `if self.pointer_bytes() == 8 { i64 } else { i32 }` sites in `expr.rs`/`place.rs` with the shared size type, including `sizeof`, slice/index byte offsets, GEPs, spec-narrow offsets, and pointer loads. Audit the neighboring pointer/int cast helpers at the same time: `reinterpret_leaf` and integer-to-pointer lowering must cast to the actual requested pointer type and use LLVM address-space casts when pointer address spaces differ.
5. **Carry code pointers through function values and dynamic dispatch.** Make `llvm_function_type` consume the target-aware leaf mapping; keep hidden sret/data pointers in address space 0. Update `vtable_for` to store code-pointer elements and update dynamic-call loading to read that code-pointer type before the indirect call. Verify ordinary function references, function-pointer parameters/results, raw-pointer <-> function-pointer casts, and spec vtables no longer assume every pointer is LLVM AS0.
6. **Finish LLVM target-machine selection.** Add AVR to `triple_for`, with `avr-none` -> `avr-unknown-unknown`; keep the current mappings for AArch64 Linux and x86-64 Windows. Replace the unconditional `llvm::supports` path with one real target-machine setup path backed by LLVM registration. Keep `initialize_all`, install the target machine's triple/data layout on the module before declarations, preserve current hosted relocation behavior, and select LLVM's default relocation mode for AVR rather than forcing PIC.
7. **Make target-conditioned inline asm exhaustive.** Add AVR to `register_class`/`status_clobbers`; keep non-x86 dialect behavior. Do not invent AVR instruction parsing or a second assembler. Preserve the existing rule that LLVM integrated-assembler/register-constraint rejection is a normal emission error.
8. **Expose/document the completed behavior, not a second CLI design.** Add `omgc` CLI unit coverage for `--target=aarch64-linux`, `--target=x86_64-windows`, and `--target=avr-none`; retain malformed/unknown-target coverage. Update the CLI and architecture docs to state the supported target flow, 16-bit AVR width, generic AVR baseline, code/data address-space handling, and LLVM-as-support-authority. Do not change the default target or add host/sysroot/linker behavior.
9. **Perform object-only acceptance verification.** Compile one small target-neutral Omega package (no platform imports, no inline asm) with the three requested targets, then a second smoke package that exercises `usize`/`sizeof` plus a function value/indirect call so AVR's 16-bit and code-pointer paths are crossed. Inspect emitted LLVM IR for the target triple/data layout and inspect the `.o` headers for object format/machine. Do not link or execute these cross-target objects in this task.

## Testing
- **New/changed cases:**
  - `omega-analyzer/src/target.rs` unit tests: `avr-none`/canonical display, `pointer_bytes == 2`, and supported-arch diagnostic text.
  - `omega-analyzer/src/resolved_type/tests.rs`: exact 16-bit `isize`/`usize` integer domains plus existing 32/64 behavior.
  - `omega-analyzer/src/layout.rs` tests and `omega-codegen/src/abi.rs` tests where needed: a function value still occupies exactly one pointer-width leaf, now tagged as a code/function pointer for backend lowering.
  - `omgc/src/cli.rs` tests: all three requested `--target` forms select the expected shared `Target`; an unknown arch/OS still fails before compilation.
  - Keep any LLVM-specific code-pointer/address-space checks at the codegen component layer; do **not** create a root cross-target execution case in `tests/` yet.
- **Specification trace:** `docs/language/types-and-primitives.md` already owns the observable rule that `isize`/`usize` have target pointer width. Function-pointer/raw-pointer cast semantics remain those already specified by the cast/FFI chapters; the new LLVM address-space work only makes that existing representation contract valid on AVR.
- **Negative/diagnostic cases:** malformed/unknown Omega targets remain parse errors; a known target whose LLVM backend is unavailable in the compiler build must return a normal unsupported-target/code-generator error, never panic or fall back to the host. Target-specific invalid inline asm remains a normal emission diagnostic.
- **Regression coverage:** run focused analyzer/codegen/CLI Rust tests first, then the existing default-target suite to ensure the new 16-bit/code-pointer distinctions do not change x86-64 Linux behavior. Function-pointer casts, indirect calls, vtables/dynamic dispatch, pointer arithmetic, `sizeof`, and C/foreign convention tests are the highest-value regressions.
- **Commands/target coverage:**
  - Run the relevant Cargo tests for `omega-analyzer`, `omega-codegen`, and `omgc`, followed by `just test-all` on the normal default target.
  - Acceptance matrix with actual `omgc`: emit both `--emit=ir` and `--emit=obj` for `aarch64-linux`, `x86_64-windows`, and `avr-none`.
  - IR inspection must show the expected backend target: AArch64 Linux triple, x86-64 Windows/MSVC triple, and generic AVR triple/data layout with 16-bit pointers/program address space.
  - Object inspection should use `llvm-readobj --file-headers` when available (or `file` plus `readelf -h`/`objdump -f`): AArch64 Linux must be an AArch64 ELF relocatable object, x86-64 Windows an x86-64 COFF object, and AVR an AVR ELF relocatable object. Header inspection proves format/machine; the emitted IR triple/data layout proves the exact backend target configuration that produced it.
  - No foreign-target link/run, QEMU, Docker platform runner, or hardware test is required for acceptance in this task.
