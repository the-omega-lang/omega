# Gap-backed atomics

## Task Description
- **Deliverable:** Add Omega's first atomic-operation API as ordinary `core` capability gaps, plus fixed-width `std` wrapper types built entirely on those gaps. No parser, analyzer, MIR, LLVM atomic intrinsic, or backend atomic lowering is introduced.
- **Purpose:** Make atomicity an explicit property supplied by the selected platform rather than an ISA/backend promise. A platform may implement the same contract with native atomic instructions, LL/SC or CAS loops, interrupt masking, an OS/kernel primitive, or locking; portable `core`/`std` code sees one stable operation-level interface.
- **Chosen direction:**
  - `runtime/core/atomic.omg` owns the ordering types and one width capability per fixed storage width: `Atomicity8`, `Atomicity16`, `Atomicity32`, and `Atomicity64`. The width names are intentional: the capability is about an N-bit atomic location, not specifically an unsigned integer wrapper.
  - Mutating gap operations take `*mut` pointers and `load` takes an immutable pointer. Atomics do not become a back door for changing an immutable Omega binding; callers that want operation-level atomics on plain storage explicitly provide mutable storage.
  - Do **not** pass an `AtomicOp` enum through `rmw`. Gaps are separately compiled/link-time-resolved calls, so a runtime operation tag would add an avoidable dispatch branch inside `plat`. Give each operation its own gap function (`exchange`, `fetch_add`, `fetch_xor`, etc.).
  - Do **not** use one ordering enum whose invalid combinations panic. Define `AtomicLoadOrdering`, `AtomicStoreOrdering`, and `AtomicRmwOrdering`, each containing only meaningful variants. This makes invalid load/store ordering states unrepresentable and avoids making every atomic operation retain a `PanicHandler` dependency merely to validate a runtime enum.
  - `compare_exchange`/`compare_exchange_weak` take an `AtomicRmwOrdering` for the success path and an `AtomicLoadOrdering` for the failure path. Omega does not impose C/C++'s “failure may not be stronger than success” restriction: each path requests its own minimum guarantee, and a platform may strengthen either path when its primitive cannot express the pair exactly.
  - Gap RMW functions return the **previous** value. `compare_exchange` returns `Result<T, T>`: `Ok(previous)` on exchange and `Err(observed)` on failure. Weak compare-exchange may fail spuriously; a platform may implement weak as strong.
  - Platforms may always provide stronger ordering/serialization than requested. In particular, a lock-backed implementation that is effectively sequentially consistent satisfies `Relaxed`, `Acquire`, and `Release` requests; Omega promises minimum ordering, not an exact amount of reordering freedom.
  - `runtime/std/atomic.omg` exposes `AtomicU8/U16/U32/U64`, `AtomicI8/I16/I32/I64`, and `AtomicBool`. Their methods call the width gaps directly; wrappers are convenience/storage encapsulation, not the source of atomicity.
  - The existing generic `runtime/plat/libc` package remains intentionally **unfilled** for the new gaps. There is no honest libc-only implementation of this contract in the current platform layer without introducing an architecture-specific implementation or a new runtime dependency such as libatomic/pthreads. Do not smuggle x86 assembly or an undeclared external runtime into a package documented as libc-only. Concrete production platform glue is added by the platform that can actually uphold the contract; tests use local glue only to exercise the core/std surface.
- **Rejected alternatives:**
  - LLVM/backend atomics or compiler intrinsics: rejected because atomicity is owned by the Omega platform seam, not codegen.
  - Atomic wrapper/type as the fundamental mechanism: rejected; raw operation-level gaps remain directly usable on mutable primitive storage.
  - `rmw(ptr, AtomicOp, rhs, ...)`: rejected because separate compilation prevents relying on cross-gap constant folding and turns a compile-time-known operation into runtime dispatch.
  - One `AtomicOrdering` plus runtime panic for invalid operation/order pairs: rejected because it preserves invalid states and would pull panic capability into otherwise valid atomics.
  - Requiring hardware/natural alignment: rejected. Omega's current layout model does not guarantee the stronger address alignment hardware atomics often want, and `docs/issues/known-issues.md` explicitly records that `@layout(align = n)` is not yet a real transitive address guarantee. A platform that fills a width gap must handle every location valid for ordinary Omega access at that width, emulating when necessary rather than leaking ISA alignment restrictions into the portable API.

## Technical Details
- **Initial context boundary:**
  - Runtime/library: `runtime/core/`, `runtime/std/`, and platform capability behavior under `runtime/plat/`.
  - Architecture: `docs/architecture/runtime-and-platform.md` and `docs/architecture/testing-and-validation.md`.
  - Normative behavior: `docs/language/gaps-and-glue.md`, new atomic semantics documentation, plus `docs/language/bindings-and-mutability.md` only as the existing `*T`/`*mut T` contract.
  - Omega source syntax: `docs/guide/quick-reference.md` and the current runtime macro patterns.
  - Known constraint: the `@layout(align = n)` issue in `docs/issues/known-issues.md`; do not expand this task into fixing aggregate alignment.
- **Affected files/symbols:**
  - New `runtime/core/atomic.omg`:
    - exposed enums `AtomicLoadOrdering { Relaxed, Acquire, SeqConsistent }`, `AtomicStoreOrdering { Relaxed, Release, SeqConsistent }`, and `AtomicRmwOrdering { Relaxed, Acquire, Release, AcquireRelease, SeqConsistent }`;
    - `Atomicity8/16/32/64` gaps, preferably generated by one item-position macro that receives the gap identifier plus the matching unsigned/signed primitive types explicitly rather than trying to concatenate tokens;
    - each width gap provides `load`, `store`, `exchange`, `compare_exchange`, `compare_exchange_weak`, `fetch_add`, `fetch_sub`, `fetch_and`, `fetch_or`, `fetch_xor`, `fetch_min_unsigned`, `fetch_max_unsigned`, `fetch_min_signed`, and `fetch_max_signed`;
    - unsigned storage operations use `u8/u16/u32/u64`; signed min/max use the corresponding `i8/i16/i32/i64` pointer/value type so signed ordering is explicit rather than inferred from unsigned bit patterns.
  - New `runtime/std/atomic.omg`:
    - exposed fixed-width integer wrappers and `AtomicBool`;
    - exposed aliases to the three `core::atomic` ordering enum types so a `std::atomic` user can import the wrappers and their ordering vocabulary from one module without creating duplicate types;
    - fixed-width wrapper bodies should be generated with ordinary `ident`/`type`/`path` macro parameters where that removes duplication. This does **not** solve `usize/isize/pointer` selection, because the missing capability is target-width selection/conditional generation rather than identifier substitution.
  - `docs/language/README.md` + new `docs/language/atomics.md` for the observable atomic/memory-order contract.
  - `docs/architecture/runtime-and-platform.md` for the durable ownership rule: atomic calls remain ordinary gap symbols and LLVM does not own or reconstruct their semantics.
  - `docs/guide/core-library.md`, `docs/guide/standard-library.md`, and `docs/guide/platform-glue.md` for module/API/platform usage and the current libc platform's deliberate lack of atomic glue.
  - New root conformance packages `tests/t35_atomics/` and `tests/t35b_atomic_errors/` (names may follow the repository's exact local naming convention, but keep the next `t35` slot and positive/negative split).
- **Interfaces/invariants:**
  - No compiler crate gains an “atomic” semantic type, checked-node variant, MIR instruction, LLVM atomic instruction, or target atomic-capability table.
  - A gap call remains an ordinary direct external function call. Current codegen treats ordinary external calls conservatively with memory side effects; platform asm is likewise already emitted with a mandatory memory clobber. Atomics may therefore be compiler-ordering-stronger than requested today, especially for `Relaxed`; that is an accepted consequence of keeping semantics out of LLVM. Do not add backend special cases merely to recover relaxed optimization freedom in this task.
  - Every operation is indivisible with respect to other atomic operations on the **same starting address and width** supplied through this API. Concurrent overlapping atomic accesses of different widths/starting addresses are outside the guarantee, as are concurrent ordinary loads/stores to bytes being atomically accessed.
  - Each atomic location has a modification order. Acquire/release synchronization and `SeqConsistent` ordering are minimum observable guarantees; `SeqConsistent` operations participate in one global total order consistent with each execution context's program order and the per-location modification order.
  - `load` only accepts load orderings; `store` only accepts store orderings; RMW/exchange/successful compare-exchange only accept RMW orderings. Compare-exchange failure is a load and therefore takes `AtomicLoadOrdering`.
  - A strong compare-exchange fails only when the observed value differs from `expected`. A weak one may also fail spuriously and returns the value it observed in `Err` either way.
  - Every `fetch_*`/`exchange` returns the value that existed immediately before that atomic modification. Min/max are atomic RMWs even when the selected result equals the old value.
  - A platform may block and may serialize unrelated locations; lock-freedom is **not** promised. Core/std atomic operations themselves must not allocate or route through `GlobalAllocator`; a platform implementation may use pre-existing/static/OS synchronization state but must not introduce hidden Omega heap allocation as part of an atomic call.
  - A platform filling `AtomicityN` implements the complete width contract. If the ISA cannot perform some member directly, the platform emulates it (CAS/LL-SC loop, lock, interrupt masking where semantically sufficient, OS service, etc.) or does not provide that width gap.
  - Do not add `@layout(align = ...)` to atomic wrappers in this task. Correctness cannot depend on it under the current known layout limitation; the platform contract must already cope with ordinary Omega addresses. Revisit wrapper over-alignment only after the existing layout issue is solved project-wide.
- **Out of scope:**
  - `AtomicUsize`, `AtomicIsize`, `AtomicPtr<T>`, pointer-width gap selection, or new macro/conditional-compilation features needed to express them cleanly.
  - Standalone hardware/compiler fences, `consume`, wait/notify atomics, lock-free capability queries, 128-bit atomics, floating-point atomics, and generic `Atomic<T>`.
  - A production implementation for a specific ISA/OS, restructuring `runtime/plat/libc`, or adding libatomic/pthread dependencies. The new contract is ready for those platform-specific follow-ups without compiler changes.
  - Fixing Omega's existing alignment/layout propagation issue.
- **Risks/open questions:**
  - None for this plan. If implementation discovers that an operation cannot be expressed through the existing gap/glue ABI without compiler help, stop rather than adding an atomic backend escape hatch; that would contradict the chosen ownership model and requires a new architecture decision.

## Implementation Plan
1. Add `runtime/core/atomic.omg`. Define the three exposed operation-specific ordering enums and import `core::result::Result`. Add an item macro that takes `(GapName, UnsignedType, SignedType)` and expands one complete width gap; invoke it for 8/16/32/64. Use `*mut` for every modifying operation, keep `load` on `*T`, return previous values from all RMW members, use `Result<U, U>` for compare-exchange, and give signed/unsigned min/max distinct members. Do not introduce `AtomicOp`, validation helpers, panic paths, or compiler hooks.
2. Add `runtime/std/atomic.omg`. Re-export the three ordering types with exposed aliases. Use macros to generate the four unsigned and four signed wrapper structs, keeping the backing field hidden. Give wrappers a `new` constructor, `load`, `store`, `exchange`, strong/weak compare-exchange, and the applicable `fetch_*` methods. Integer wrappers map directly to their matching width gap; signed wrappers use the unsigned width operations for bit-preserving load/store/exchange/add/sub/bitwise/CAS and the signed min/max gap members for comparisons. Implement `AtomicBool` manually over `Atomicity8`, exposing only load/store/exchange/CAS and boolean `fetch_and`/`fetch_or`/`fetch_xor`. Mutating wrapper methods use `*mut self`; `load` uses `*self`. Do not expose the backing field, `get_mut`, or a non-atomic accessor in this first surface.
3. Specify the semantics in new `docs/language/atomics.md` and index it from `docs/language/README.md`. Define atomic location identity, per-location modification order, the minimum guarantees of the three ordering enums, acquire/release synchronization/happens-before at the level needed for message-passing, the single total order for `SeqConsistent`, RMW/compare-exchange result rules, weak spurious failure, permitted strengthening, and the rule excluding concurrent ordinary or differently-sized overlapping accesses. Make clear that the API is expressed through `core` gaps but its observable semantics are not implementation-defined.
4. Update `docs/architecture/runtime-and-platform.md` with the atomic capability seam: core declares width gaps, std wraps them, a selected platform owns the implementation, and codegen remains unaware. Record that ordinary gap calls/opaque asm are intentionally conservative compiler memory barriers today, so `Relaxed` may optimize less than an intrinsic-based design without becoming semantically incorrect.
5. Update `docs/guide/core-library.md`, `docs/guide/standard-library.md`, and `docs/guide/platform-glue.md`. Show where `atomic.omg` lives, distinguish raw operation-level core atomics from std wrappers, explain that mutating operations require mutable storage/pointers, state that wrappers do not imply lock-free behavior, and explicitly state that `runtime/plat/libc` currently opts out of the new atomic gaps rather than pretending to provide a portable implementation it does not have.
6. Add `tests/t35_atomics/` with local test glue for only the widths needed by the case (at least 8-bit for `AtomicBool` and 32-bit for signed/unsigned integer coverage). The local glue may use straightforward single-threaded Omega operations because the case is testing gap/wrapper API behavior and return semantics, not claiming to validate a production concurrent implementation. Exercise raw `Atomicity32` calls and the std wrappers: load/store, exchange returning old value, arithmetic/bitwise fetch operations, signed and unsigned min/max, strong compare-exchange success/failure, weak compare-exchange without assuming a spurious failure, `AtomicBool`, and a compare-exchange whose failure ordering is stronger than its success ordering to lock in Omega's independent-path rule.
7. Add `tests/t35b_atomic_errors/` for the type-level ordering boundary: e.g. passing an `AtomicStoreOrdering` to `load`, a load ordering to `store`, or a load ordering as the compare-exchange success ordering must fail with the ordinary type-mismatch diagnostic. Do not add runtime “invalid ordering panics” because those states should no longer be constructible through the API.
8. Build core/std with the new modules and run focused tests. Confirm that existing non-atomic programs still link with the unchanged `runtime/plat/libc` object despite its not filling any `AtomicityN` gap; this protects the existing “unused capability does not force glue” invariant. Finish with the normal full gate.

## Testing
- **New/changed cases:**
  - `tests/t35_atomics/`: end-to-end compile/link/run coverage of raw core operations plus `AtomicU32`, `AtomicI32`, and `AtomicBool`; include old-value return semantics and compare-exchange `Result` payloads.
  - `tests/t35b_atomic_errors/`: compile-failure coverage proving operation-specific ordering types reject invalid category combinations at type checking rather than at runtime.
  - No compiler-local Rust tests are required unless implementation unexpectedly changes compiler code; this feature should remain runtime/library-only.
- **Specification trace:** `tests/t35_atomics` exercises the operation/result rules in new `docs/language/atomics.md`; `t35b` proves its ordering-category typing rules. The current test harness has no thread primitive, so it cannot prove inter-thread indivisibility or acquire/release visibility; those guarantees are platform-contract requirements and need dedicated concurrent tests alongside the first real production atomic glue.
- **Negative/diagnostic cases:** Assert the exact ordinary type-mismatch diagnostic for wrong ordering-category arguments. Do not accept a generic compile failure and do not add panic-output expectations.
- **Regression coverage:** Existing `t17_gaps_and_glue` protects the generic gap mechanism; `t23_inline_assembly` protects the opaque/memory-clobber asm behavior platform implementations may rely on; the full suite protects that adding unfilled atomic gaps to core/std does not make unrelated programs require new platform symbols.
- **Commands/target coverage:** After `omgc`, `core.o`, `std.o`, and `plat.o` are built, run `./bin/test-runner t35_atomics t35b_atomic_errors` (using the final exact directory names), then `just test-all`. No architecture-specific production target matrix is required until a concrete `runtime/plat/*` implementation is added; that follow-up must test real concurrent behavior on every platform it claims to support.
