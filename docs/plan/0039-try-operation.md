# Postfix Try Operator (`?`) and Core `Result`

## Task Description
- **Deliverable:** Add postfix `expression?` for the canonical `core::option::Option<T>` and a new canonical `core::result::Result<T, E>`, preserving the try operation explicitly through AST, HIR, and the analyzer's checked representation; resolve all propagation semantics in `omega-analyzer`; lower the checked try operation to ordinary CFG/return behavior in `omega-mir`; support the same checked operation in compile-time evaluation; and add diagnostics, docs, and conformance coverage.
- **Purpose:** Make typed failure propagation concise while keeping Omega's semantic tree useful to future tooling. An LSP or other consumer of `omega-hir`/`omega-analyzer` must still be able to observe that the user wrote `?`, inspect its operand/result/error types, and associate diagnostics with the operator instead of receiving a compiler-invented `match`/temporary/`return` tree.
- **Chosen direction:**
  - Add `runtime/core/result.omg` with an ordinary `exposed enum Result<T, E>` containing `Ok { exposed value: T; }` and `Err { exposed error: E; }`. Keep `Option<T>`'s existing `None` / `Some { value: T }` representation unchanged unless implementation evidence requires a compatibility fix.
  - `?` is a normal postfix suffix at the existing highest-precedence postfix tier and chains left-to-right with calls, indexing/slicing, and field access. The lexer already has `TokenKind::Question`; this is parser/representation work, not a lexical change.
  - Preserve the construct one-for-one as `Expression::Try` -> `HirExpr::Try` -> `CheckedExpr::Try`. Carry the `?` token span separately from the whole expression span so diagnostics/tooling can identify the operator itself.
  - The analyzer, not MIR, owns the meaning of the operator. `CheckedTry` records the analyzed operand, whether it is canonical `Option` or `Result`, the already-resolved source success/failure variant and payload indices, the enclosing canonical fallible return type and destination failure variant/field, and (for `Result`) the already-decided `E -> F` coercion required by propagation. The checked node's own type is the unwrapped success `T`.
  - `Option<T>?` requires the enclosing function to return canonical `Option<R>`. `Some` yields `T`; `None` returns that enclosing `Option<R>::None`.
  - `Result<T, E>?` requires the enclosing function to return canonical `Result<R, F>`. `Ok` yields `T`; `Err` extracts `E`, applies exactly the ordinary existing implicit/expected-type coercion that an `E` value may undergo where `F` is explicitly expected, then returns the enclosing `Result<R, F>::Err`. This permits the existing explicit-destination anonymous-enum injection/widening used by `E -> enum E | F` without adding a whole-container `Result<T,E> -> Result<T,F>` conversion.
  - Factor the analyzer's current expected-type coercion decision into reusable semantic data (for example `CheckedCoercion` / `CheckedCoercionStep`): one helper decides whether/how `found -> expected` is legal and records representation-changing facts such as anonymous-enum member injection/remapping or spec-object slots; another applies that plan to an ordinary `CheckedExprNode`. Existing `coerce_to_expected` becomes a caller of those shared helpers. `CheckedTry` stores the plan for its not-yet-projected error payload. MIR and const-eval execute this plan but never re-run semantic compatibility/conformance decisions.
  - MIR does **not** gain `MirExpr::Try` or a try terminator. `omega-mir` is already the CFG boundary: it evaluates the checked operand once, branches on the resolved enum variant/tag, sends the failure path through the function's existing return/defer exit chain, and joins the success payload back into the surrounding expression. This is the correct stage for the source-level try operation to disappear.
  - Compile-time evaluation consumes checked expressions directly, so `comp_eval.rs` must interpret `CheckedExpr::Try` from the same resolved metadata/coercion plan rather than depending on MIR or reimplementing type rules. A failure inside an evaluated Omega function raises the evaluator's existing `Signal::Return`, preserving compile-time `defer` behavior.
  - Reject `?` inside a `defer` body because its failure arm exits the enclosing function, matching the existing prohibition on explicit `return` there.
- **Rejected alternatives:**
  - Do not lower `?` during semantic analysis into synthetic `CheckedBlock`/`CheckedMatch`/`CheckedStmt::Return`; that erases source semantic identity too early and makes checked-tree consumers reconstruct an operation the analyzer already understood.
  - Do not add a MIR-native try instruction. Once semantic facts are resolved, try is ordinary backend-independent control flow, which is exactly `omega-mir`'s responsibility.
  - Do not make MIR infer whether `E` converts to `F`, discover `Option`/`Result` by spelling, or recompute anonymous-enum remaps/spec coercion. Those are analyzer-owned facts under the existing “resolve once, read back later” rule.
  - Do not introduce a Rust-like user-extensible `Try`/residual spec protocol in this task.

- **Initial context boundary:**

  - Semantics/checked vocabulary: `compiler/omega-analyzer/src/analysis/exprs/`, `analysis/mod.rs` (`coerce_to_expected` and anonymous-enum conversion helpers), `checked.rs`, `resolved_type.rs`, `error/`, `dead_code.rs`; [`docs/architecture/semantic-analysis.md`](docs/architecture/semantic-analysis.md).
  - CFG lowering: `compiler/omega-mir/src/lower/function.rs`, `lower/function/expr.rs`, `lower/function/control_flow.rs`, `lower/function/defer.rs`; [`docs/architecture/mir-and-codegen.md`](docs/architecture/mir-and-codegen.md).
  - Compile time: `compiler/omega-analyzer/src/comp_eval.rs` + `comp_eval/tests.rs`; [`docs/language/compile-time-evaluation.md`](docs/language/compile-time-evaluation.md); [`docs/architecture/types-layout-and-const-eval.md`](docs/architecture/types-layout-and-const-eval.md).
  - Core library: `runtime/core/option.omg`, new `runtime/core/result.omg`, and [`docs/guide/core-library.md`](docs/guide/core-library.md).
  - No `omega-codegen`, ABI, layout, linker, allocator, platform, or driver implementation change is expected.
- **Affected files/symbols:**
  - `omega-parser`: add a source-oriented try AST node containing `base` + `operator_span`; extend `parse_postfix_loop` for `TokenKind::Question`; recurse into the base in `macros/expander.rs`; re-export the new type from `prelude.rs` as required. Do not alter `[?]T` type parsing.
  - `omega-hir`: add `HirTry`/`HirExpr::Try` with the original outer `HirId`, source span, operator span, and lowered operand. HIR lowering remains infallible and performs no fallible-type recognition.
  - `omega-analyzer::checked`: add `CheckedTry`/`CheckedTryKind` (or equivalent) as semantic output vocabulary plus the reusable checked coercion-plan vocabulary required to describe `Result` error propagation without constructing a fake source expression.
  - `omega-analyzer::analysis::exprs`: dispatch `HirExpr::Try` to a focused try analyzer (prefer a small `try_operator.rs`). Analyze the operand as its own fallible expression rather than passing the outer unwrapped expected type directly into it; the resulting success `T` is then exposed to the surrounding expected-type machinery normally.
  - `omega-analyzer::analysis/mod.rs`: split the current expression-mutating coercion path into “decide/record coercion” and “apply coercion to a checked expression” without changing existing coercion semantics. Keep anonymous-enum compatibility/remap and spec-object conformance selection single-sourced here.
  - `omega-analyzer::error/{kind,render}.rs`: add precise diagnostics for unsupported operand type, missing/non-fallible enclosing return, Option/Result family mismatch, unpropagatable `Result` error `E -> F`, and use inside `defer`. Anchor the primary diagnostic on the stored `?` span where practical.
  - `omega-analyzer::dead_code`: recurse through `CheckedTry` and account for the source success/failure variant/body-field reads and destination failure variant construction represented implicitly by the node, so checked-tree usage accounting remains complete.
  - `omega-mir`: treat `CheckedExpr::Try` as a checked control-flow expression. Add a `lower_try_*` path that can either lower to a fresh result/merge for nested expression use or write into an existing `BlockDestination`, matching the existing `if`/`match` control-flow pattern. Update the defer structural visitor to recurse into the try operand.
  - `comp_eval.rs`: evaluate the operand once, inspect its resolved variant, return the success payload, or construct/coerce the destination failure value and emit `Signal::Return`. Execute the stored coercion plan; do not call semantic resolution from the evaluator. Keep the existing outer-`comp` control-flow boundary robust: an escaping control-flow signal must become a structured compile-time-evaluation failure rather than a compiler panic if this feature exposes that pre-existing edge.
  - `runtime/core/result.omg`: ordinary generic enum only; exposed core declarations already participate in core's ambient lookup, so do not add a compiler prelude registry solely for `Result`.
  - Docs: update grammar/operator semantics/core-library docs and record the checked-vs-MIR ownership explicitly in semantic-analysis/MIR architecture docs; add `?` to compile-time-evaluation support once `comp_eval` handles checked try nodes.
- **Interfaces/invariants:**
  - **Tooling boundary:** the exact user-written `?` remains a distinct AST/HIR/checked node. Semantic analysis may annotate it heavily but must not replace it with invented source-level control flow. Checked-tree consumers should not need MIR to know a try operator existed.
  - **One semantic owner:** only the analyzer decides canonical fallible identity, source/destination variant indices, payload fields, `E -> F` legality, anonymous-enum remaps, and any spec-object coercion slots. MIR/const-eval consume these decisions.
  - **Canonical types only:** recognize `core::option::Option` and `core::result::Result` through resolved declaration/module identity, then validate/read their known variant/field names. Transparent aliases work because aliases resolve to the same enum identity; user-defined lookalikes do not receive special behavior.
  - **No new positional dependency:** `Option` currently has a load-bearing variant order for iteration; try must not extend that accident. Resolve `None`/`Some` and `Ok`/`Err`, plus `value`/`error`, by canonical metadata during analysis and store the resulting indices.
  - **Single evaluation:** the operand is evaluated exactly once. MIR must materialize it before using both tag and payload; const-eval evaluates it once into one `ConstValue`.
  - **Success type is independent:** source `T` is the `?` expression's value type and need not equal enclosing `R`. The surrounding expression/assignment/call/return continues to apply normal expected-type rules to that yielded `T`.
  - **Payload-only propagation conversion:** `Result` propagation may convert extracted `E` to explicit destination `F`; it must never implement this by coercing/rebuilding the source `Result<T,E>` as a `Result<T,F>` first.
  - **No cross-family propagation:** Option requires Option return; Result requires Result return. No implicit `Option<T> <-> Result<T,E>` conversion is introduced.
  - **Defer semantics:** a runtime or compile-time try failure follows the same function-exit/defer sequence as an explicit return. MIR failure branches must target the existing exit chain after storing the return value; const-eval failure uses its existing return signal so registered defers still run.
  - **No backend/runtime privilege:** `Result` has ordinary enum layout/ABI. `?` needs no allocator, libc, runtime helper, codegen special case, ABI rule, or emitted symbol.
  - **Expected-type inference scope:** do not invent new generic inference that synthesizes an `Option<expected>` / `Result<expected, ?>` expectation solely because `?` exists. Analyze the operand with the current inference facilities and expose its resolved success type to the outer context; a broader inference enhancement is separate work.
- **Out of scope:**
  - User-defined fallible types, a `Try`/residual spec, customizable propagation, or overloaded `?`.
  - Implicit whole-container `Result<T,E> -> Result<T,F>` conversion/covariance, including anonymous-enum widening of the container itself.
  - Implicit `Option`/`Result` interconversion.
  - A broad `Option`/`Result` helper API (`map`, `and_then`, `unwrap`, etc.). Explicit conversion helpers may be added later as ordinary core methods without changing compiler semantics.
  - Exceptions, `try {}` blocks, `catch`, panic/unwind, effects, or async behavior.
  - MIR/LLVM optimization of statically known `Some`/`Ok`/`None`/`Err` branches beyond ordinary optimization.
- **Risks/open questions:** None for the implementer to decide ad hoc. If representing the full existing expected-type coercion as reusable semantic data would require changing coercion behavior rather than merely factoring its decision/application, stop and escalate; do not narrow `?` to a one-off anonymous-enum-only conversion or let MIR re-type-check the payload as a shortcut.

## Implementation Plan
1. **Add the ordinary core `Result` type and document its minimal surface.** Create `runtime/core/result.omg` with `Result<T,E>::Ok.value` and `Result<T,E>::Err.error`; update `docs/guide/core-library.md`. Leave `Option` unchanged unless a focused test proves a necessary fix.
2. **Add source-preserving postfix syntax through parser and HIR.** Introduce `Try` AST/HIR shapes with the operand and `?` span, add `?` to `parse_postfix_loop`, recurse through it during macro expansion, and add syntax-only HIR lowering. Update `docs/language/grammar.md` and postfix precedence text. Parser/HIR tests must prove chaining and that the try node survives lowering.
3. **Create a reusable semantic coercion plan before implementing Result propagation.** Refactor `coerce_to_expected`/anonymous-enum/spec coercion internals so the analyzer can first decide an already-resolved conversion from source type to expected type and then apply that decision to an actual checked expression. Preserve all existing callers/behavior. The plan must carry every representation-changing fact downstream consumers need; no downstream resolver/conformance query is allowed.
4. **Add `CheckedExpr::Try` as durable semantic output.** Define checked metadata for source family/variants/payloads, destination failure construction, operator span, and optional Result error coercion. Update `docs/architecture/semantic-analysis.md` to state explicitly that a checked try remains source-semantic control flow and stores resolved propagation facts rather than desugaring to a synthetic match/return tree.
5. **Analyze `Option`/`Result` try semantics without desugaring.** Add the focused try analyzer: analyze the base once as an expression, recognize canonical source and enclosing return families by resolved identity, resolve named variants/fields to indices, reject `in_defer_body`, compute the success type, and for Result ask the shared coercion planner whether source `E` can inhabit destination `F`. Emit `CheckedExpr::Try` directly. Add precise error variants/rendering.
6. **Keep semantic/usage visitors complete.** Extend checked-tree usage/dead-code traversal for the explicit try node and its implicit enum accesses/construction. Audit exhaustive `HirExpr`/`CheckedExpr` matches touched by the new variants; update only structural visitors that actually consume the new node.
7. **Lower checked try in MIR, not before MIR.** Add `CheckedExpr::Try` to the control-flow lowering vocabulary. Evaluate/materialize the operand once, branch using the analyzer-selected source variants/tags, project the success payload and feed it into the current/fresh `BlockDestination`, and on failure construct the enclosing `None`/`Err`, applying the stored coercion plan to `Err.error`, store the function return value, then jump to `exit_chain_start`. Reuse/refactor the existing return-value/exit-chain helper instead of duplicating defer-return mechanics. Do not add any `MirExpr::Try` or LLVM handling. Update `docs/architecture/mir-and-codegen.md` with this ownership boundary.
8. **Interpret the same checked operation in compile-time evaluation.** Add `CheckedExpr::Try` handling to `comp_eval.rs`: one operand evaluation, resolved variant dispatch, success payload extraction, stored-coercion execution, destination failure construction, and existing `Signal::Return` propagation. Add focused evaluator tests proving a called compile-time Omega function using `?` returns `Ok`/`Err` or `Some`/`None` correctly and runs defers on failure. Replace any newly reachable outermost escaping-signal panic with a structured comp-eval diagnostic rather than inventing different propagation semantics. Update compile-time docs/architecture accordingly.
9. **Add architecture-preservation and end-to-end conformance tests.** Besides parser/HIR tests, add a component test that inspects analyzer output and asserts the source `?` is still `CheckedExpr::Try` after semantic analysis, then verify MIR lowering produces ordinary CFG. Add root `t32` success/runtime semantics and `t32b` exact-negative diagnostics; finish with the normal full gate.

## Testing
- **New/changed cases:**
  - `compiler/omega-parser/tests/try_operator.rs`: assert AST association for `call()?`, `value?.field`, `nested??`, `fallible?()`, and interaction with a lower-precedence binary expression; assert the stored operator span is the `?` token.
  - `compiler/omega-hir/tests/lowering.rs`: prove `Expression::Try` remains `HirExpr::Try`, with a distinct outer `HirId`, preserved operand, and preserved `?` span; do not accept a lowered `match`/codeblock as equivalent.
  - A focused analyzer/driver component test (prefer `compiler/omega-driver/tests/try_operator.rs` if using the real core package is simpler than constructing analyzer fixtures) must inspect the checked function and prove it contains `CheckedExpr::Try` with resolved Option/Result metadata and Result error-coercion metadata. Lower that checked program to MIR in the same test or a MIR-focused test and prove the operation has become CFG rather than surviving as a source-semantic IR node.
  - `compiler/omega-analyzer/src/comp_eval/tests.rs`: cover `CheckedTry` success/failure in evaluated function calls, Result error conversion where representable at compile time, and defer execution on a try-generated return signal.
  - Root `tests/t32_try_operator/`:
    - `Option`: `Some` yields payload; `None` exits the enclosing `Option<_>` function.
    - `Result`: `Ok` yields payload; `Err` exits the enclosing `Result<_,_>` function.
    - `Result<_, ErrorA>?` and `Result<_, ErrorB>?` inside a function returning `Result<_, enum ErrorA | ErrorB>` both work, proving payload conversion into the explicit anonymous-enum error type without whole-Result conversion.
    - `Option<void>` and/or `Result<void,E>` success works.
    - a side-effecting operand proves exactly-once evaluation.
    - postfix chaining works at runtime.
    - a previously registered `defer` executes on a `?` failure path.
    - transparent aliases of canonical Option/Result retain try behavior.
    - a function that is itself evaluated through `comp` can use `?` and produce the same fallible result semantics.
  - Root `tests/t32b_try_operator_errors/` with exact `expected.stderr`:
    - non-fallible operand such as `42?`;
    - use where the enclosing function does not return Option/Result;
    - Option operand in Result-returning function and vice versa;
    - `Result<T,E>?` where `E` cannot implicitly inhabit destination `F`;
    - `?` inside `defer`;
    - user-defined lookalike `Option`/`Result` proving canonical identity is required;
    - direct assignment/return of `Result<T,E>` to `Result<T, enum E | F>` still fails;
    - direct Option/Result cross-conversion still fails.
