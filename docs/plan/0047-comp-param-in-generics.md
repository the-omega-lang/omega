# Compile-Time Value Generics

## Task Description
- **Deliverable:** add first-class compile-time value parameters to Omega generics using `comp`, so declarations such as `struct Buffer<comp N: usize, T> { data: [N]T; }` can be instantiated with compile-time-known values (`Buffer<10, i32>`, `Buffer<SIZE, i32>`) and those values participate in monomorphization, type identity, layout, inference, and symbol identity without becoming runtime parameters.
- **Purpose:** make value-dependent types expressible without introducing a second metaprogramming mechanism. A generic `comp` parameter is a storage-less compile-time binding available while analyzing the instantiated declaration, so existing compile-time evaluation and ordinary fixed-array/layout machinery remain the source of truth and the abstraction compiles away completely.
- **Chosen direction:**
  - Extend every existing generic-parameter position with an explicit parameter kind: ordinary type parameter, or `comp NAME: TYPE`. The value type is mandatory; type parameters keep their existing bounds/default behavior.
  - Generic argument lists become ordered mixed arguments. A semantic generic argument is either a resolved type or a canonical typed compile-time value; do not encode values as fake `ResolvedType`s.
  - Keep source-level value arguments deliberately small in this change: signed/unsigned integer literals, `bool`, `char`, or a path naming a `comp` value/parameter. A parameter default uses the same value syntax (`comp N: usize = 16`, `comp M: usize = N`). Arbitrary computation is written once as an ordinary `comp` binding and that binding is passed by name. This avoids embedding unlowered expression AST inside type syntax while still using the full existing comp evaluator to produce arguments.
  - Initially allow generic `comp` parameter types whose resolved type has simple canonical cross-query identity: integer primitives (including `isize`/`usize`), `bool`, and `char`, including aliases resolving to those types. Reject floats, pointers/references, strings/slices, aggregates, and other values until they have an explicit stable equality/hash/mangling policy. Structure the semantic/mangling representation so more value kinds can be added later without changing the type-vs-value generic model.
  - The declared comp-parameter type is authoritative. Resolve/evaluate each value argument left-to-right under that expected type and canonicalize integer values to it when exactly representable. This intentionally makes `comp size := 123; Buffer<size, i32>` valid for `comp N: usize`; a negative/out-of-range/non-integer value is rejected rather than truncated or wrapped.
  - A comp generic participates in inference only from compile-time structural information. In particular, matching raw `[N]T` against concrete `[4]i32` binds `N = 4` and `T = i32`; ordinary runtime values never infer a comp generic.
  - Preserve the current mangling bytes for declarations whose generic arguments are all types. Add a distinct mixed/value-generic encoding only when at least one comp argument is present, so this feature does not silently migrate every existing generic symbol.
- **Rejected alternatives:**
  - Do not lower a comp generic as a hidden runtime function parameter or stored field; that would add runtime cost and make layout/identity depend on runtime data.
  - Do not represent `10` as a synthetic type or overload `Vec<ResolvedType>` with sentinel types. Values need their own equality, hashing, diagnostics, substitution, and mangling contracts.
  - Do not make generic arguments full arbitrary expressions in this change. `Type`/`ExprPath` are currently shared parser syntax inside HIR; embedding parser `Expr` nodes there would bypass normal HIR expression lowering/IDs and entangle the type grammar with comparison parsing. A later expression syntax (if desired, especially for dependent forms such as `[N + 1]T`) should be designed deliberately rather than smuggled in here.
  - Do not use `ConstValue` directly as the query/mangling key. It includes values (notably floats/references and richer aggregates) that do not currently have the required `Eq + Hash` and stable cross-compilation identity semantics.

## Technical Details
- **Initial context boundary:**
  - Syntax/HIR: `compiler/omega-parser`, `compiler/omega-hir`; start from `compiler/omega-parser/src/ast/generics.rs`, `ast/type.rs`, `ast/identifier.rs`, `parser/item/functions.rs`, `parser/type.rs`, `parser/expression.rs`, `compiler/omega-hir/src/hir.rs`, and `lower/item.rs`.
  - Semantics/const evaluation: `compiler/omega-analyzer`; start from `resolved_type.rs`, `resolver.rs`, `generics.rs`, `context.rs`, `analysis/mod.rs`, `analysis/paths.rs`, `analysis/calls/generic.rs`, `analysis/literals.rs`, and `analysis/consts.rs`.
  - Generic instantiation/query ownership: `compiler/omega-driver`; start from `items/mod.rs` (`ItemKey`), `items/resolution.rs`, `bodies.rs`, `resolver.rs`, `aliases.rs`, and `conformances/`.
  - Symbol contract: `compiler/omega-mangle/src/{symbol,grammar,encode,decode,display}.rs` and `compiler/omega-mir/src/mangle.rs` plus `mangle/semantic.rs`.
  - Normative docs: `docs/language/generics.md`, `compile-time-evaluation.md`, `types-and-primitives.md`, `grammar.md`; usage examples in `docs/guide/quick-reference.md`. Architecture contracts: `docs/architecture/{parsing-and-hir,semantic-analysis,types-layout-and-const-eval,module-driver-and-linkage,symbol-mangling,testing-and-validation}.md`. `ARCHITECTURE.md` currently describes item query identity in terms of type arguments and must not remain stale.
- **Affected files/symbols:**
  - `GenericParam` / `HirGenericParam` need a kind that distinguishes a type parameter from `comp` plus its required value type, and a default whose syntax matches that kind. `normalize_static_spec_params` in `omega-analyzer/src/generics.rs` must continue synthesizing an ordinary type parameter explicitly.
  - `Type::Generic(Path, Vec<Type>)` and `ExprPath.generic_args: Vec<Type>` need a source `GenericArg` representation capable of carrying a syntactically unambiguous type, scalar comp literal, or ambiguous path. A bare path such as `i32` versus `SIZE` is resolved according to the corresponding declared parameter kind, not guessed by the parser. Fixed-array size syntax (`Type::SizedArray(_, String)` / `parse_array_size`) must similarly accept a scalar value literal/path so `[N]T` reaches semantic resolution rather than requiring decimal text.
  - `ModuleResolver` generic metadata and `GenericSignature`, `GenericLiteralSignature`, and `GenericOwnerFunctionSignature` currently split generic names/defaults into type-only vectors. Replace those parallel lists with ordered parameter descriptors that retain kind, declared comp type, bounds, and defaults. Type-path resolution also needs parameter metadata before it can resolve mixed explicit arguments; keep this a metadata query, not a second item-instantiation engine.
  - Add a semantic `ResolvedGenericArg` (type vs comp) and a canonical scalar comp-value representation with `Eq + Hash`. Replace generic-instantiation identity fields currently named/stored as `Vec<ResolvedType>` (`ItemKey.type_args`, nominal resolved types, checked generic definitions/functions, spec applications/bounds/conformances, MIR generic metadata) with ordered mixed generic arguments; rename `type_args` to `generic_args` where the field is no longer type-only instead of leaving misleading terminology.
  - Replace type-only substitutions (`[(Ident, ResolvedType)]`, `HashMap<Ident, ResolvedType>`) with a generic substitution that holds both type and comp bindings. `Analyzer::with_substitution` should install type bindings through `Context::define_type` as today and install comp bindings through the existing `Storage::Comp`/`Context::set_comp_value` path using a fresh synthetic declaration id. References to `N` in a body then naturally become `CheckedExpr::Const`; MIR/codegen receive no runtime parameter.
  - Extend `resolve_generic_arg_list`, generic call/aggregate inference, `resolve_inferred_type_args`, `unify_generic_type`, expected-generic logic, alias substitution, spec/conformance substitution, and conformance target matching to operate on parameter kinds. For dependent arrays, a literal size must match the concrete length and a comp-generic size binds from the concrete `ResolvedType::SizedArray` length. Omitted trailing parameters use defaults of their own kind; unresolved required comp parameters report inference failure just like unresolved type parameters.
  - `Context::resolve_type` must resolve a symbolic fixed-array size through the active comp binding/global comp resolver, require an integer compile-time value, and preserve the existing `u32` fixed-array length limit. A comp generic itself may hold the full range of its declared scalar type; the `u32` check occurs only when that value is used as an array length.
  - `omega-analyzer/src/type_key.rs` and spec/conformance canonicalization must include canonical comp arguments wherever generic applications contribute to semantic identity. Diagnostics in `omega-analyzer/src/error/kind.rs` and driver diagnostics must stop saying “type argument” where the rule applies to mixed generic arguments and add focused errors for unsupported comp-parameter type, expected compile-time value, non-comp runtime binding, non-representable value, and wrong argument kind.
  - In `omega-mangle`, introduce a dependency-free mixed generic argument/value model. Keep the existing `TAG_GENERIC` type-list encoding for all-type argument lists; add a new grammar form/tag for mixed/value lists with explicit argument/value tags. `omega-mir::mangle::semantic` converts `ResolvedGenericArg` into this model. Equal canonical comp arguments must mangle identically and different values/types must not collide.
- **Interfaces/invariants:**
  - `Buffer<10, i32>` and `Buffer<11, i32>` are distinct semantic types, distinct `ItemKey`s, and distinct monomorphized symbol identities; repeating `Buffer<10, i32>` converges on the same query/cache entry even if `10` came through a differently typed integer `comp` binding that normalized exactly to the declared `usize` parameter.
  - Generic parameter/argument order remains positional and left-to-right. Explicit arguments retain authority; omitted remainder arguments are filled by inference/defaults. Type bounds apply only to type parameters. A comp parameter's declared type/default is resolved with the substitutions available from preceding parameters, following the existing generic ordering rules.
  - A normal runtime binding is never “constant enough” merely because its initializer is obvious. `value := 42; Buffer<value, i32>` is rejected; `comp value := 42; Buffer<value, i32>` is accepted when representable.
  - Generic comp bindings are immutable, storage-less, and usable everywhere an ordinary comp value is legal while analyzing the instantiated declaration (array lengths, ranges, `comp` evaluation, conditionals, etc.). No runtime ABI parameter, allocation, libc, platform service, or backend-specific mechanism is introduced.
  - Fixed arrays still resolve to `ResolvedType::SizedArray(_, u32)` before MIR/layout. LLVM/codegen should therefore require no new dependent-type representation.
  - Existing pure-type generic source remains valid and existing pure-type mangled names remain byte-for-byte stable.
  - Aliases remain transparent: aliasing/forwarding a declaration with comp generics must preserve its parameter kinds, defaults, inference, and resulting underlying identity rather than create alias-specific value semantics.
- **Out of scope:**
  - Full arbitrary expressions directly inside generic argument/array-size syntax (`Foo<N + 1>`, `[N * 2]T`) and any new brace/`comp` expression delimiter for them.
  - Runtime-dependent values, dependent values that cannot be reduced during semantic analysis, and specialization/partial evaluation based on runtime data.
  - Float, pointer/reference, string/slice, aggregate, function, or enum generic values in the initial supported set; adding one requires an explicit canonical identity and mangling rule.
  - Changing the existing `u32` maximum fixed-array length, generic specialization policy, or monomorphization ownership/linkage model.
- **Risks/open questions:**
  - Do not broaden the accepted comp-value type set ad hoc during implementation. If a required existing language construct needs a richer value kind, stop and define its equality/hash/mangling semantics before adding it.
  - If preserving the legacy all-type generic mangling bytes proves impossible with the mixed model, stop before changing the encoder grammar and treat that as an explicit ABI migration decision rather than silently rewriting existing symbols.

## Implementation Plan
1. **Define the source and HIR model for parameter kinds and restricted value syntax.** In `omega-parser`, add the `comp NAME: TYPE` branch to `parse_generic_param`, retain ordinary type bounds, support same-kind defaults, and introduce a mixed `GenericArg` plus reusable scalar-comp-value syntax for integer/bool/char/path values. Update `Type::Generic`, `ExprPath.generic_args`, fixed-array syntax, parser display/helpers/traversals, and `omega-hir` lowering/copies. Preserve the existing expression generic-vs-comparison speculative commit/rollback rule; only the set of things accepted inside `<...>` grows.
2. **Introduce canonical semantic generic arguments.** In `omega-analyzer::resolved_type`, add the type-vs-comp generic argument representation and an `Eq + Hash` canonical scalar value carrying its resolved declared type. Centralize validation/normalization from `ConstValue`/literal/path to a declared comp-parameter type, including exact integer range checks and the supported-type gate. Keep this separate from general `ConstValue` so ordinary compile-time evaluation is not weakened to satisfy hashability.
3. **Expose ordered generic parameter metadata before argument resolution.** Refactor `ModuleResolver` and the three generic signature structs to return parameter descriptors rather than type-only names/default arrays; add/use the equivalent metadata query for generic type/item paths. Update driver implementations and alias forwarding so a caller can zip raw explicit arguments with parameter kinds before deciding whether a path denotes a type or a comp value.
4. **Make substitution and type resolution mixed.** Replace type-only substitution plumbing in analyzer/driver with one ordered generic substitution. Install comp entries as real `Storage::Comp` bindings in analyzer scopes using fresh synthetic ids and their canonical value, while preserving the existing type binding path. Extend fixed-array resolution from decimal text to compile-time scalar value syntax, resolving local/generic/global comp paths and enforcing nonnegative/`u32` size at the array-use site.
5. **Extend explicit resolution, defaults, and inference.** Update expression/type generic argument resolution, generic calls, aggregate literals, owner generics, aliases, specs, conformances, and primitive/conformance templates to consume mixed arguments. Infer comp parameters only from dependent structural positions (starting with fixed-array lengths and mixed nominal generic applications), keep type inference unchanged for type parameters, and fill omitted same-kind defaults after inference. Ensure argument-count/order diagnostics continue to follow the established left-to-right explicit-generics rules.
6. **Promote mixed arguments into all semantic/query identities.** Change `ItemKey`, resolved nominal/spec applications, checked generic items/functions, conformance substitutions/keys, `type_key` generation, and MIR metadata from type-only argument vectors to mixed generic arguments. Audit equality/hash/canonical-order code so comp values participate anywhere concrete type arguments currently distinguish two instantiations. Keep concrete array layout downstream: once substitution resolves `[N]T`, existing layout/MIR/codegen still see the ordinary sized-array type.
7. **Extend symbol mangling without migrating existing generic ABI.** Add `MangleGenericArg`/canonical scalar value forms and a new mixed/value generic grammar tag in `omega-mangle`; decode/display/round-trip it and teach `omega-mir`'s semantic adapter and symbol helpers to consume mixed arguments. Encode all-type generic lists with the legacy form exactly as before; use the new form only when a comp argument is present.
8. **Add diagnostics and documentation as part of the semantic change.** Add precise errors for invalid comp parameter type, wrong generic argument kind, runtime/non-comp value, failed integer normalization, invalid dependent array length, and unresolved comp inference; update generic wording that is no longer type-only. Update the normative language chapters and grammar, quick reference, and the affected architecture documents/item-key wording so the language rule, compile-time behavior, query identity, and mangling contract agree.

## Testing
- **New/changed cases:**
  - Add `tests/t34_comp_generics/` as the positive language-conformance package. Cover a `NumericArrayWrapper<comp N: usize, T>`-style field `[N]T`, instantiation from both a literal and `comp my_comp_size := 123`, use of `N` inside a generic body, distinct sizes/layout-visible behavior for different `N`, repeated equal instantiations, a comp default, alias forwarding, and a generic function whose `N`/`T` are inferred from a concrete `[N]T` argument.
  - Add `tests/t34b_comp_generic_errors/` for rejected observable source: runtime binding as comp arg, type/value kind mismatch, unsupported comp-parameter type (including float), negative/out-of-range integer normalization, a comp value that cannot normalize to the declared type, dependent array length outside `u32`, too many/missing arguments, and a comp parameter that inference/defaults cannot determine. Assert the intended diagnostic reason, not merely compilation failure.
  - Add parser tests in `omega-parser` for `comp N: usize`, mixed `<10, i32>` / `<SIZE, T>` arguments in type and expression paths, bool/char/signed literals, comp defaults, `[N]T`, nested angle lists, and rollback/commit around comparisons so the recent explicit-generics disambiguation remains intact.
  - Add analyzer/driver component tests for canonical integer normalization, mixed substitution installing `Storage::Comp`, fixed-array unification binding `N`, `ItemKey` equality/distinction by comp value, alias/default behavior, and spec/conformance matching with comp arguments where those paths are supported.
  - Add `omega-mangle` round-trip/display tests for mixed arguments plus a regression fixture proving a representative existing all-type generic symbol encodes byte-for-byte identically; add MIR mangling adapter coverage showing differing comp values produce differing symbols.
- **Specification trace:** `docs/language/generics.md` defines comp parameter declaration, positional mixed arguments, defaults/inference, and value identity; `docs/language/compile-time-evaluation.md` defines comp arguments/parameters as compile-time storage-less values; `docs/language/types-and-primitives.md` defines `[N]T` as a fixed array only when `N` resolves at compile time and fits the existing size domain; `docs/language/grammar.md` records the new productions.
