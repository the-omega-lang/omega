# Transparent Aliases

## Task Description
- **Deliverable:** Add a top-level `alias` declaration that gives another source name to an existing type, spec/spec conjunction, function, macro, or module/path without creating a new semantic declaration, type identity, function identity, symbol, ABI entity, or runtime value.
- **Purpose:** Let Omega name long/specialized types, preserve or adapt generic type templates, rename functions/macros/modules, name static/dynamic spec conjunctions, and deliberately re-export declarations through an independently visible name while keeping aliases compile-time-only.
- **Chosen direction:** Treat aliases as name-resolution indirection, not ordinary items. Parse/lower a structural alias declaration, index it in driver-owned alias state, and erase it during semantic resolution by returning the target's existing identity. Type-form aliases expand under the alias declaration's module/generic environment before contextual type semantics are applied; this is required so `alias AB = spec A + B` is indistinguishable from spelling `spec A + B` directly, including `*spec` dynamic-object resolution and static-spec parameter/bound behavior. A plain alias of a generic declaration inherits that declaration's generic behavior; an alias with its own generic list is a type/spec alias template whose parameters are substituted into its type-form RHS. Function aliases preserve overload sets and generic inference rather than selecting or cloning one function.
- **Rejected alternatives:** Do not lower aliases into duplicate structs/specs/functions, synthetic wrappers, new linker symbols, or mangled alias identities. Do not teach the parser to resolve/classify targets or manufacture `ResolvedType` values. Do not special-case named spec aliases only at individual bound/pointer call sites; normalize aliases before the existing positional spec rules so literal and aliased spellings share one mechanism. Do not implement re-export by globally bypassing the target declaration's visibility.

## Technical Details
- **Initial context boundary:** Start in `compiler/omega-parser`, `compiler/omega-hir`, `compiler/omega-analyzer`, and `compiler/omega-driver`; read `docs/language/{lexical-structure,grammar,modules-and-imports,visibility,generics,specs-and-conformance,macros}.md` plus `docs/architecture/{parsing-and-hir,semantic-analysis,module-driver-and-linkage}.md`. MIR/codegen/mangling are verification boundaries, not implementation owners, because aliases must disappear before checked output.
- **Affected files/symbols:**
  - `compiler/omega-parser/src/lexer.rs`, `ast/item.rs`, `parser/item.rs`, `parser/item/functions.rs`, `prelude.rs`: add reserved `alias`, an AST alias declaration, generic-parameter parsing reuse, visibility support, `=`/`;` grammar, and an alias target representation that preserves a plain path versus a structural `Type` without semantic classification. Reject expression/value syntax and irrelevant annotations/modifiers at parse time where syntactically knowable.
  - `compiler/omega-hir/src/hir.rs` and `lower/item.rs`: add `HirAlias` carrying id/span/name/visibility/generics/structural target. Remove `Lowerer::desugar_spec_static_params` as the semantic authority; HIR must keep literal `spec ...` parameters structural so semantic normalization can treat literal and aliased forms identically.
  - `compiler/omega-driver/src/modules.rs`: index aliases separately from concrete `ModuleIndex.items`/overloads and imports; diagnose alias/local-alias redeclarations using ordinary top-level declaration rules; keep aliases out of concrete item/emission sweeps. Add the raw-AST alias view needed while constructing the pre-HIR macro environment.
  - `compiler/omega-driver/src/resolver.rs` and `items/{mod.rs,resolution.rs}`: add ordered/memoized alias query state with an explicit resolution stack and cycle diagnostics. Alias lookup must be namespace-aware and able to yield a module path, concrete item identity, generic declaration/overload forwarding information, or a type-template target without creating an `ItemKey` for the alias itself. `declared_item_visibility`, similarity lookup, generic-signature queries, spec lookup, overload lookup, and ordinary item resolution must follow aliases where their namespace permits it.
  - `compiler/omega-analyzer/src/resolver.rs`, `context.rs`, `analysis/{mod.rs,paths.rs,specs.rs,items/mod.rs,calls/generic.rs,calls/overload.rs}`: expose/consume the alias resolver contract; expand type aliases under definition-site module context and alias-generic substitution before ordinary type-position validation; reject targets that resolve to runtime/global/`comp` values or unsupported declaration kinds; preserve target `ResolvedType` cells, spec cells, function `decl_id`s, overload candidates, and storage rather than synthesizing alias identities.
  - `compiler/omega-analyzer/src/error/*` and driver diagnostics: add focused errors for invalid alias target kind, generic arity/bounds failures, and alias cycles, reported at the alias/use site with the underlying resolution failure preserved when useful.
  - Macro environment construction in `compiler/omega-driver/src/modules.rs`: allow a plain-path alias to bind a macro name before expansion. Reuse the target macro body/defining module but give the expansion binding the alias's name and effective visibility so an `exposed` macro alias cannot use a hidden macro's original visibility to smuggle narrower definition-site dependencies.
- **Interfaces/invariants:**
  - An alias is top-level only. It never names a local binding or arbitrary expression, and a path target resolving to `Storage::Global`/`Storage::Comp` is invalid. A function-valued foreign/function declaration (`Storage::Function`) is valid; gaps and other unlisted declaration kinds remain invalid.
  - A type-form RHS may be any legal type syntax, including primitives, pointers/arrays/function types, generic applications, `spec A + B`, and `*spec A + B`. A plain path RHS can name a module, type/spec declaration, function/overload set, generic declaration, macro, another alias, or a fully qualified top-level path such as `std::string::String`; resolve it from the alias declaration site, without requiring a separate import merely to create the alias. Keep `root`/`self`/`super` behavior consistent with the module-navigation rules if those anchors are admitted in alias-target grammar.
  - `alias MyGenericType = GenericType;` forwards the target declaration's generic arity/defaults/bounds/inference. `alias MySpecificType = GenericType<i32>;` is non-generic and resolves directly to that specialization. `alias StringKeyedMap<V> = HashMap<*str, V>;` owns `V` and expands/substitutes the RHS; its resolved identity is exactly the resulting `HashMap<*str, V>`. Alias-owned bounds/defaults are validated like other generic parameters but do not create nominal identity.
  - Alias cycles are always illegal, including cycles hidden behind pointer/type constructors: because an alias creates no nominal cell, `alias A = *A` has nothing concrete to point at. Do not reuse the ordinary recursive-type indirection exception to permit alias cycles.
  - Re-export is deliberate capability transfer. First check the alias declaration's visibility against the caller. After that succeeds, resolve/access its target from the alias declaration's module under normal target visibility; callers must not be forced to satisfy the underlying top-level declaration visibility again. Thus `exposed alias Public = Hidden;` is valid when `Hidden` is visible at the alias declaration and external users may name it through `Public`. This does not change the target declaration's own visibility, member visibility, spec-member visibility, or symbol identity.
  - A module/path alias exposes the path name only; traversing `Alias::Item` still checks `Item`'s own visibility. A direct item alias is what re-exports that item.
  - Alias chains preserve the final target identity and each alias is its own visibility gate. `reveal` remains an explicit use-site bypass for the alias/target lookup where written; do not turn aliasing into a permanent global reveal.
  - Overloaded function aliases forward the complete candidate set visible from the alias declaration site; overload resolution still happens at the call site using the existing scorer. Generic function aliases forward the target's existing generic inference and concrete `decl_id`/`ItemKey` materialization. No wrapper body is created.
  - Macro aliases are compile-time name bindings only. Expansion tokens retain the original macro definition module/body for hygiene, but alias visibility is the effective macro visibility for dependency-leak checks.
  - A spec declaration remains a declaration of one spec only. `alias AB = spec A + B` names a conjunction; it does not resurrect `spec AB = A + B`, create a conformance target named `AB`, or allocate a spec cell for the conjunction. Canonical spec-shape ordering/dedup uses final spec identities/arguments, never alias spelling.
  - Normalize callable signatures after alias expansion but before generic query identity/inference. Replace the current HIR-only static-spec-parameter desugaring with one semantic normalization path so `f(x: spec A + B)` and `f(x: AB)` synthesize the same anonymous bounded generic behavior. Cache/route this normalized signature through driver generic-signature/item queries rather than duplicating the rule in calls, bounds, and body checking.
  - Resolved aliases must never appear in `CheckedItem`, MIR, `MirLinkage`, mangling inputs, vtable identity, layout identity, or emitted symbols. Using an alias may cause the normal underlying generic/function/type materialization, but under the target's canonical module/name/id.
- **Out of scope:** Do not add local `alias` statements, value/expression aliases, member-method/enum-variant aliases, alias-generated wrapper functions/symbols, opaque/newtype semantics, or a new `spec` declaration-composition syntax. Do not redesign existing import shadowing rules beyond the collision handling required for alias declarations.
- **Risks/open questions:** No user decision is required for the requested surface. If implementation discovers that an explicitly generic alias must target a non-type namespace (for example a new syntax for partially specializing a generic function), stop rather than inventing syntax; the requested examples only require explicit generic parameters for type/spec alias templates, while plain function aliases must transparently preserve the target function's genericity.

## Implementation Plan
1. Add and document the source grammar. Introduce `TokenKind::Alias`, `Item::Alias`/AST target structures, parser routing after optional visibility, and generic-list reuse. Add parser tests for basic/path/type/spec/generic forms and rejection of expression-shaped RHS/local use. Lower aliases one-for-one to `HirAlias`; keep their targets unresolved and structural.
2. Establish driver-owned alias indexing/query state before wiring use sites. Add alias entries to `ModuleIndex` (separate from concrete item positions), deterministic `InProgress / Resolved / Failed` state plus ordered cycle stack, declaration-site visibility/module data, and validation sweeps so unused invalid aliases still diagnose. Make alias resolution follow alias chains without ever building an alias `ItemKey` or type cell.
3. Implement namespace-transparent path/item forwarding. Extend `ModuleResolver` with the minimal alias query/target data needed by analyzer; make ordinary item/type/spec/module path resolution, overload candidate lookup, generic function/literal/static signature lookup, typo candidates, and visibility queries recognize aliases. Resolve target paths from the alias declaration module and return the underlying semantic identity. Reject globals/`comp` values/gaps and other unsupported target kinds.
4. Implement generic/type-template aliases as structural substitution. Resolve alias generic arguments/defaults/bounds, substitute them into the alias RHS, then run the existing type resolver from the alias definition environment. Ensure bare aliases to generic declarations forward their target generic metadata, while explicit alias generic templates can fix/reorder/nest type arguments without changing target identity. Make aggregate construction/static methods/`sizeof` and other type consumers observe the resulting canonical target type, not an alias wrapper.
5. Unify static spec positional semantics after alias expansion. Remove `Lowerer::desugar_spec_static_params`; introduce a normalized callable-signature query/helper at the analyzer/driver seam that expands aliases first, then converts an outermost static `spec ...` parameter into the existing anonymous bounded-generic model. Feed the same normalized generics/params to `item_generics`, `generic_function_signature`, signature collection/body checking, and generic call inference so literal and alias spellings cannot diverge. Make generic-bound/spec-application resolution flatten a type alias to `spec A + B` through this same structural expansion rather than teaching bound checking a second alias format.
6. Add macro alias support at the pre-expansion boundary. During `Driver::macro_env`, scan/index raw alias declarations that can target macros, resolve chains/cycles from the declaration site, and insert an aliased `MacroDefinitionStmt` view using the original body/defining module but alias name/visibility. Ensure macro-only aliases are considered valid declarations without forcing a nonexistent ordinary item target, and that nested expansion/hygiene continues through existing `ExpansionState` machinery.
7. Enforce re-export visibility precisely. Gate callers on alias visibility, resolve the target using the alias module's access rights, and then pass through the underlying identity. Ensure direct hidden-item re-exports work, module aliases do not accidentally expose hidden children, overload candidate visibility is fixed from the alias declaration site, and macro dependency visibility uses the alias visibility. Keep member/spec-member visibility checks tied to the real declaring owner.
8. Keep aliases out of later phases and update documentation. Confirm compilation/body/output sweeps skip `HirAlias` as a non-emitted declaration and that no checked/MIR/mangling representation is added. Add `docs/language/aliases.md`; update the language index, lexical keywords, grammar, modules/imports re-export statement, visibility, generics, specs/conformance, macros, and quick reference. Update `parsing-and-hir.md`, `semantic-analysis.md`, and `module-driver-and-linkage.md` to record the alias query boundary and the relocation of static-spec parameter normalization; remove stale statements that Omega has no alias/re-export mechanism.
