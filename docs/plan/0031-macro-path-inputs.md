# Macro `path` Fragment Inputs

## Task Description
- **Deliverable:** add `path` as a macro parameter fragment kind, so signatures such as `macro re_export($path: path, $ident: ident)` accept exactly Omega's ordinary `path` grammar and substitute the captured tokens unchanged into the macro body.
- **Purpose:** let macros accept qualified names as one syntactic argument without weakening them to `expr`/`type` or splitting a path into identifiers. Reuse Omega's existing path grammar so anchored and unanchored paths stay consistent everywhere and macro hygiene/provenance continues to come from the existing token-substitution model.
- **Chosen direction:** extend `omega-parser`'s existing `FragmentKind`/fragment-validation dispatch with `Path`, and validate arguments by running the shared `parser::parse_path` production to EOF. This makes `$p: path` accept the normative `path` production from `docs/language/grammar.md` -- including unanchored paths, `root::`, `self::`, and chained `super::` -- with no macro-specific path representation or rules. Substitution remains token-for-token, so caller-origin metadata on the captured path is preserved automatically.
- **Rejected alternatives:** do not parse paths with a macro-only token scanner, model a captured path as a new AST value, or route this through HIR/analyzer resolution; all would duplicate the parser's path authority or change the macro expansion boundary. Do not lift the existing ban on `import` inside macro bodies as part of this feature: `macro my_import($p: path) => { import $p; }` still conflicts with the normative macro rule that expansion cannot mutate the caller's import namespace. Supporting macro-generated imports is a separate language-semantics decision.

## Technical Details
- **Initial context boundary:** start in `compiler/omega-parser` (`ast/item.rs`, `parser/contextual.rs`, `parser/macro_syntax.rs`, `parser/mod.rs`, `macros.rs`, and `tests/macros.rs`). Normative context is `docs/language/macros.md`, the `path` production in `docs/language/grammar.md`, and the contextual-keyword rule in `docs/language/lexical-structure.md`; implementation context is `docs/architecture/parsing-and-hir.md`. Use `docs/architecture/testing-and-validation.md` for test layering. HIR, analyzer, driver, MIR, and codegen stay closed because the expanded token stream reparses into existing AST forms before HIR lowering.
- **Affected files/symbols:**
  - `compiler/omega-parser/src/ast/item.rs::FragmentKind`: add `Path` alongside `Expr`, `Type`, and `Ident`.
  - `compiler/omega-parser/src/parser/contextual.rs`: add `PATH` and include it in `ALL`, preserving `path` as an ordinary identifier outside the macro-fragment-kind position.
  - `compiler/omega-parser/src/parser/macro_syntax.rs::parse_fragment_kind`: recognize contextual `path` and include it in the expected-fragment diagnostic.
  - `compiler/omega-parser/src/macros.rs::validate_fragment`: dispatch `FragmentKind::Path` to the existing `crate::parser::parse_path`; retain the existing full-consumption/error checks so non-path suffixes or malformed paths fail as `FragmentMismatch`.
  - `compiler/omega-parser/tests/macros.rs`: add focused component coverage for successful and rejected `path` fragments and expansion shape/provenance behavior.
  - `docs/language/macros.md` and `docs/language/lexical-structure.md`: document the fourth fragment kind and contextual use of `path`; `docs/language/grammar.md` already owns the path production and should remain the definition of what the fragment accepts.
  - `docs/guide/quick-reference.md`: add a short `$p: path` macro example or fragment-kind mention so the user-facing reference exposes the feature.
  - `tests/t18_macros/`: extend the existing macro conformance package with a real `$path: path` use, preferably the `re_export` pattern, without introducing macro-generated imports.
- **Interfaces/invariants:** `path` means the existing grammar production, not `type-path` or arbitrary expression syntax; validation must consume the entire macro argument. Existing generic variadic handling should work unchanged for `$paths: path...`. Captured tokens retain caller origin while macro-authored tokens retain definition origin; adding this fragment must not retag or reconstruct path tokens. `path` remains contextual, not a globally reserved keyword. Expansion still has no declared output kind and still reparses at the invocation position.
- **Out of scope:** macro-generated imports; new path syntax; generic/type-path fragment semantics; qualified macro invocation syntax; HIR/analyzer/module-resolution changes; changes to macro visibility, hygiene, repetition, argument splitting, or diagnostics infrastructure.
- **Risks/open questions:** none for the requested `path` fragment itself. If the intended deliverable also requires the `my_import` pseudocode to compile, stop and escalate: that requires deliberately revising the current macro/import semantic rule rather than deleting `ImportInMacroBody` as an incidental parser restriction.

## Implementation Plan
1. **Extend the fragment-kind vocabulary without reserving `path`.** Add `FragmentKind::Path` in `compiler/omega-parser/src/ast/item.rs`; add `parser::contextual::PATH` and register it in `ALL`; update `parser/macro_syntax.rs::parse_fragment_kind` to accept `$name: path` and update the expected-kind text to list `path`. Keep recognition contextual so ordinary declarations/fields/functions named `path` continue to parse.
2. **Reuse the ordinary path parser for invocation validation.** In `compiler/omega-parser/src/macros.rs::validate_fragment`, map `FragmentKind::Path` to `crate::parser::parse_path(&mut p)`. Preserve the existing `p.is_eof()` and parser-error checks: this is what makes the fragment accept every current ordinary path shape while rejecting expressions, calls, incomplete `::` chains, and other trailing syntax without inventing macro-specific rules. Do not transform the captured tokens after validation; let the existing `Bindings`/`render` path substitute them with caller provenance.
3. **Add parser/component tests around the new boundary.** In `compiler/omega-parser/tests/macros.rs`, prove `$p: path` accepts a multi-segment unanchored path plus `root::`, `self::`, and multi-`super::` anchors, and that the expansion reparses as the expected existing path-bearing AST. Add at least one invalid argument that starts like a path but has non-path trailing syntax so the full-consumption contract is covered, and assert the `FragmentMismatch` reason. Include a small variadic `path...` case if practical to prove the generic repetition/binding machinery needs no special handling. The existing `contextual_keywords` test should automatically cover `path` once `PATH` is added to `ALL`.
4. **Add end-to-end language conformance for the intended use.** Extend `tests/t18_macros` with a macro such as `re_export($path: path, $ident: ident)` that emits an alias target built from `$path::$ident`, then use the generated alias so successful compilation/execution proves path capture, substitution, reparse, and downstream resolution work together. Keep the case focused and do not use `import` in the macro body; existing coverage must continue to prove that such imports are rejected.
5. **Update the language/user documentation to the implemented contract.** In `docs/language/macros.md`, change the fragment-kind list to `expr`, `type`, `ident`, and `path`, and state that `path` accepts exactly the ordinary `path` grammar (including explicit anchors) while preserving caller-origin hygiene. Add `path` to the contextual-keyword list in `docs/language/lexical-structure.md`. Update the macro section of `docs/guide/quick-reference.md` with a concise path-fragment example. Do not change `docs/architecture/parsing-and-hir.md` unless implementation unexpectedly changes ownership or the expansion/reparse contract.

## Testing
- **New/changed cases:** parser component tests in `compiler/omega-parser/tests/macros.rs` for accepted unanchored/anchored paths, full-token rejection, and optional variadic paths; existing `compiler/omega-parser/tests/contextual_keywords.rs` should prove `path` remains a legal ordinary identifier. Extend root `tests/t18_macros` with an executable re-export/path-substitution case.
- **Specification trace:** the root conformance case proves the new fragment rule documented in `docs/language/macros.md` while the accepted syntax is defined by `docs/language/grammar.md`'s `path` / `path-anchor` productions. Contextual-keyword behavior traces to `docs/language/lexical-structure.md`. The existing macro-body import rejection in `docs/language/macros.md` remains unchanged.
- **Negative/diagnostic cases:** pass a non-path or a path followed by extra syntax to `$p: path` and assert the macro error identifies a fragment mismatch rather than accepting a prefix. Preserve the existing `import_in_a_macro_body_is_rejected_at_definition_time` test unchanged.
- **Regression coverage:** run the parser macro and contextual-keyword integration suites, then the focused `t18_macros` conformance package. No HIR/analyzer/backend-specific suite is required beyond the end-to-end case because no downstream representation or semantic contract changes.
- **Commands/target coverage:** run `cargo test -p omega-parser --test macros --test contextual_keywords`; after the normal compiler/runtime artifacts are built, run `./bin/test-runner t18_macros`; finish with `just test-all`.
