# Correct Macro Definition-Site Visibility

## Task Description
- **Deliverable:** Correct macro visibility semantics so a declaration referenced by macro-authored syntax is required to be visible from the macro's **definition site**, not from the invocation site and not merely because its visibility is at least as broad as the macro's own visibility. `runtime/core/panic.omg` must therefore be able to call the `shared` `PanicHandler::panic` directly from the exposed `panic$` macro without `reveal`.
- **Purpose:** Make visibility follow the same hygiene boundary Omega already uses for macro name resolution. An exposed macro is an abstraction boundary: callers need permission to invoke the macro, while declarations used internally by its body need only be accessible where that body was authored. `reveal` remains an explicit bypass for genuinely inaccessible declarations rather than a routine requirement for encapsulated macro implementations.
- **Chosen direction:** Treat macro visibility and macro-body dependency visibility as independent questions. A macro's `hidden`/`shared`/`exposed` modifier controls who may name/invoke the macro. Every visibility-bearing reference authored by the macro body is then checked with the macro definition module/lexical rights carried by its expansion `Origin`, just as its name lookup already is. Caller-substituted syntax keeps caller origin and caller rights.
- **Chosen direction:** Remove the `MacroDependencyTooPrivate` model entirely. There is no rule requiring an exposed macro's dependencies to be exposed, or a shared macro's dependencies to be shared. Ordinary visibility at the definition site is sufficient. This intentionally permits an exposed macro to wrap a hidden top-level helper in its own module or a shared package-private API, exactly as an exposed function can encapsulate private implementation details.
- **Chosen direction:** Keep `reveal` hygienic. A caller-side `reveal macro$()` must not grant extra access to definition-origin references inside the macro body; a `reveal` authored inside the macro body may still bypass a declaration that is genuinely not visible from the definition site. Reuse expansion origins for this distinction rather than adding a panic-specific exception.
- **Rejected alternatives:** Do not special-case `core::panic`, do not keep the current "dependency must be at least as visible as the macro" rule with an exception, and do not pre-type-check macro bodies at declaration time: macro bodies remain duck-typed token templates checked only after substitution. Do not weaken ordinary declaration visibility globally; only make the access context of macro-authored syntax match its existing definition-site name-resolution context.

## Technical Details
- **Initial context boundary:** Start with `compiler/omega-parser/src/macros.rs` and the expression AST/parser origin plumbing, `compiler/omega-hir/src/hir.rs` plus `lower/expression.rs`, `compiler/omega-analyzer/src/analysis/{mod.rs,visibility.rs,paths.rs,places/,calls/,literals.rs}` and `resolver.rs`, the matching `omega-driver` resolver/module plumbing and macro-hygiene/alias tests, and `runtime/core/panic.omg`. Normative docs are `docs/language/macros.md`, `docs/language/visibility.md`, and `docs/language/aliases.md`; implementation provenance is documented in `docs/architecture/parsing-and-hir.md`. No MIR/codegen/ABI work is in scope.
- **Current stale mechanism:** `analysis/mod.rs::{check_macro_dependency_visibility, check_macro_dependency_level}` obtains the originating macro's visibility through `ModuleResolver::macro_origin_visibility` and rejects a selected declaration when its visibility is narrower than the macro. `AnalysisErrorKind::MacroDependencyTooPrivate` and its renderer encode that obsolete rule. `omega-parser::macros::ExpansionOrigin` stores `macro_visibility` only to support this check.
- **Definition-site provenance invariant:** `Analyzer::path_module` already maps a `Path`'s `Origin` back to the macro definition module via `ModuleResolver::macro_origin_module`; unqualified roots and several qualified-path/member paths already use that accessor. Preserve this as the single source of definition-site module identity. Expansion `Origin` must continue to distinguish macro-authored tokens from substituted caller tokens and nested macro expansions.
- **Visibility-context correction:** Audit visibility decisions reached from origin-bearing syntax and make them use the accessor implied by that syntax's origin instead of `Analyzer::module_path` when the two differ. Likewise, an active `reveal` may bypass a macro-authored reference only when the reveal itself belongs to the same origin; a caller-origin reveal must not leak through the expansion boundary. Source-authored syntax with the default origin must retain normal source `reveal` behavior.
- **Member-origin gap:** Ordinary paths retain origin, but member names currently lose it: `FieldAccessExpr` stores only the field `Ident`, `HirProjection::FieldAccess` stores only the `Ident`, and `StructLiteralField` / `HirStructLiteralField` likewise omit the field token's origin. Thread the member-name origin through these existing AST/HIR shapes so `check_member_visibility` can distinguish a macro-authored `.field`/method name from a caller-substituted receiver or from source code at the invocation site. This is representation plumbing only; grammar and checked/MIR representations do not change.
- **Member visibility invariant:** For `shared`/`exposed` members, the package/module accessor must come from the member token's origin. Hidden member access must continue to obey the owner-only rule from `docs/language/visibility.md`; invoking a top-level macro from inside an owner's method must not accidentally lend that method's hidden-member privilege to a macro-authored member token. A caller-substituted member expression retains caller origin and therefore ordinary owner/module rights.
- **Resolver/reveal plumbing:** `analysis/visibility.rs::RevealState` currently stores origins but exposes `active()` globally and `has_origin()` only for the obsolete dependency-transfer rule. Refactor its use so resolver-facing visibility bypasses and direct `check_visibility` / `check_member_visibility` decisions consult the origin of the syntax being checked. Update current sites that pass `self.reveals.active()` into `ResolveItemOptions`, overload lookup, type resolution, gap-member lookup, and member checks where an origin is available. Preserve unnecessary-`reveal` warnings and nested-reveal accounting; only the authorization context changes.
- **Macro expansion metadata cleanup:** Once no semantic rule compares dependency visibility to macro visibility, remove `ExpansionOrigin::macro_visibility`, `ExpansionState::macro_visibility`, `ModuleResolver::macro_origin_visibility`, the `omega-driver` forwarding method, and the analyzer test-stub implementation. `MacroDefinitionStmt.visibility` itself remains required: it still controls macro import/invocation visibility, and macro aliases still take the alias declaration's visibility for the alias name that callers see.
- **Macro aliases:** `compiler/omega-driver/src/modules.rs::bind_macro_aliases` must continue preserving the original macro body and defining module while changing the alias name/visibility. Remove only the comment/logic assumptions that the alias visibility participates in dependency checks. An exposed alias of a hidden macro is valid when the alias declaration can see that macro, just like other exposed aliases deliberately re-export hidden targets; expansion still uses the original macro definition site's rights.
- **Diagnostics:** Delete `AnalysisErrorKind::MacroDependencyTooPrivate` and its renderer rather than replacing it with another macro-specific diagnostic. A macro-authored reference that is genuinely inaccessible from its definition site should fail through the existing ordinary visibility diagnostic (`NotVisible`, `FieldNotVisible`, `MethodNotVisible`, etc.), because that is the actual violated rule.
- **Runtime correction:** In `runtime/core/panic.omg`, remove `reveal` from `PanicHandler::panic(&info)`. The existing `shared` handler function remains deliberately inaccessible to ordinary cross-package source, while the exposed macro may call it because the macro body is authored inside `core::panic` and therefore has package access.
- **Interfaces/invariants:** Macro invocation visibility remains unchanged. Name lookup hygiene remains unchanged. Caller-substituted tokens retain caller resolution/visibility. Nested macros retain each expansion's own definition origin. `reveal` remains a local bypass and does not permanently re-export anything. No runtime cost, linkage, ABI, MIR, codegen, gap/glue matching, or symbol behavior changes.
- **Out of scope:** Do not redesign macro expansion order, imports-in-macros, path-fragment hygiene, alias semantics outside macros, hidden-member semantics themselves, or the broader `ModuleResolver` facade. Do not edit historical plans under `docs/plan/`; they record the old decision that this task is correcting.
- **Risks/open questions:** None requiring product/design input. If implementation discovers a visibility-bearing macro-authored identifier whose origin is currently discarded outside the verified field/method/struct-literal paths above, preserve that token's origin through the nearest AST/HIR representation rather than falling back to invocation-site rights or adding another visibility-level heuristic.

## Implementation Plan
1. Remove the obsolete macro-visibility dependency contract. Delete `check_macro_dependency_visibility` / `check_macro_dependency_level`, `AnalysisErrorKind::MacroDependencyTooPrivate`, its rendering, and the `macro_origin_visibility` plumbing from `omega-analyzer`, `omega-driver`, and `omega-parser::macros::ExpansionState`. Keep definition-module provenance and `MacroDefinitionStmt.visibility` intact.
2. Make ordinary path/item visibility use the same origin-derived accessor as macro name resolution. Review `analysis/paths.rs` entry points (including `resolve_qualified_value` and `resolve_gap_member`) and resolver-facing helpers in `analysis/mod.rs` so a definition-origin path is resolved and visibility-checked as code written in its definition module, while caller-origin paths keep the caller module. Remove the now-redundant post-resolution dependency-level checks.
3. Make `reveal` authorization origin-aware at visibility boundaries. Refactor `analysis/visibility.rs::RevealState` and the current `reveals.active()` visibility call sites so a reveal only bypasses a visibility-bearing reference from the same syntactic origin. Preserve normal default-origin source reveals, same-origin macro-authored reveals, nested reveal use tracking, and `UnnecessaryReveal`; ensure `reveal macro$()` cannot grant access to definition-origin internals.
4. Preserve origin for macro-authored member names that currently discard it. Capture the identifier token origin when parsing postfix field/member access and struct-literal field initializers in `omega-parser`, preserve it through macro AST reconstruction and HIR lowering, and extend `HirProjection::FieldAccess` / `HirStructLiteralField` accordingly. Update analyzer field, method, uncalled-member, generic-member, overload-member, and literal-field visibility checks to use that origin-derived access context. Give analyzer-synthesized member projections (such as internal `for` lowering helpers) the ordinary source/default origin unless a more specific existing source origin is available.
5. Correct macro-alias expectations in `omega-driver`. Keep alias target visibility checking at the alias declaration site and keep alias visibility as the caller-facing gate, but remove all dependency-level behavior/comments. Change the existing alias regression that expects `MacroDependencyTooPrivate` so an exposed alias of a locally visible hidden macro with hidden implementation dependencies succeeds.
6. Remove the unnecessary bypass from `runtime/core/panic.omg`: call `PanicHandler::panic(&info)` directly. Rebuild core as part of focused verification to prove no source-level `reveal` is needed for the abstraction.
7. Update normative documentation. In `docs/language/visibility.md`, replace the current macro "dependency must be at least as visible as the macro" section with the definition-site rule and clarify that macro visibility only gates invocation. In `docs/language/macros.md`, state that body-authored visibility is checked in the same definition environment as body-authored name resolution and that caller-substituted syntax uses caller rights. In `docs/language/aliases.md`, remove the special effective-visibility/dependency-check rule for macro aliases while retaining per-link alias-target visibility. Update `docs/architecture/parsing-and-hir.md` so `ExpansionState` provenance lists the defining module/environments, not macro visibility, and explains that semantic visibility consumes the same origin provenance as name resolution.
8. Update focused conformance/component coverage before the full gate. Prefer modifying existing macro tests where they already express the relevant rule rather than adding parallel mechanisms or panic-specific test infrastructure.

## Testing
- **Parser/HIR origin coverage:** Add focused parser/HIR assertions that a macro-expanded postfix member token and struct-literal field token retain their expansion origin through AST reconstruction and HIR lowering. Existing path/reveal-origin tests should continue proving path and reveal provenance.
- **Driver macro-hygiene changes:** In `compiler/omega-driver/tests/macro_hygiene.rs`, replace `an_exposed_macro_cannot_name_a_hidden_item` with a positive case where an exposed macro names a hidden top-level helper in its own definition module. Keep a positive macro-authored `reveal` case, but make it target something genuinely not visible from the macro definition site (for example a hidden sibling-module declaration). Keep/reshape the caller-side `reveal` case so `reveal apply$()` still cannot make that inaccessible definition-origin dependency valid and assert the ordinary visibility error rather than `MacroDependencyTooPrivate`.
- **Member-context regression:** Add a component case where a top-level macro authored outside a type emits access to that type's hidden member and is invoked from one of the type's own methods. It must still be rejected unless the macro body itself writes `reveal`, proving invocation-site `current_owner` privilege is not inherited by macro-authored member names. Add a positive `shared`/definition-site member case where practical to exercise package-level access through the same origin-aware path.
- **Alias regression:** Update `compiler/omega-driver/tests/aliases.rs::an_exposed_macro_alias_cannot_smuggle_a_narrower_dependency` into a positive capability-transfer case. Retain the separate negative coverage that an alias declaration itself cannot name a macro target it is not allowed to see.
- **Root macro conformance:** Strengthen `tests/t18_macros/` by making `defs::secret` hidden/default and `read_secret` exposed. `main` must still print `read-secret: 7` even though the caller module cannot name `secret` directly. This directly proves the documented rule and fails under the old macro-visibility comparison.
- **Panic regression:** Keep `tests/t33_panic_handler/` unchanged at the call site but run it against the updated `runtime/core/panic.omg` with no `reveal`. It proves an exposed core macro can use the shared raw handler from its definition package while an external application still reaches that handler only through the macro during ordinary source use. Keep `tests/t33b_panic_handler_errors/` proving a direct cross-package call to `PanicHandler::panic` remains rejected.
- **Negative conformance:** Add or extend a focused macro visibility error package to prove a caller-side `reveal` around a macro invocation does not grant the macro body access to a declaration unavailable at its definition site; check the existing ordinary visibility diagnostic exactly.
- **Specification trace:** The positive `t18_macros` case proves `docs/language/macros.md`/`visibility.md` definition-site body visibility; the caller-reveal negative proves the expansion boundary is hygienic; `t33_panic_handler` plus `t33b_panic_handler_errors` prove the intended abstraction: `panic$` may call the shared core handler while application source may not call it directly.
- **Regression coverage:** Run `cargo test -p omega-parser`, `cargo test -p omega-hir`, `cargo test -p omega-analyzer`, and the focused `omega-driver` macro-hygiene/alias integration tests. Then rebuild runtime artifacts and run `./bin/test-runner t18_macros t33_panic_handler t33b_panic_handler_errors` plus any new negative macro case, followed by `just test-all`.
- **Target coverage:** No backend-specific matrix is required. The change ends at frontend semantic access control; the full conformance gate is sufficient to prove runtime/core still compiles and links after removing the panic macro's `reveal`.
