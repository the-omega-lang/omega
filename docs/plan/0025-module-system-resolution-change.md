# Top-Level and Explicit Relative Module Resolution

## Task Description
- **Deliverable:** Replace Omega's implicit relative / `extern::` import model with top-level-by-default imports plus explicit `root::`, `self::`, and chained `super::` anchors, reject those three spellings as module identities, and rename the `omgc --extern` package-registration flag to `--import`.
- **Purpose:** Make imports shorter for dependencies (`import std::io::println;`), remove filesystem-shape-dependent relative lookup, and make every local-relative import state its intent explicitly. The result should be simpler to explain, deterministic across separate compilation, and free of the overloaded source-level `extern` import concept.
- **Chosen direction:** Model the prefix separately from the ordinary path (for example an import-anchor enum with top-level, package-root, self, and `super` depth variants). An unprefixed import is an absolute logical path whose first segment must be a known top-level package identity: either the package containing the importing module or a package registered with the compiler. `root::` starts at the root of the package that owns the importing module; `self::` starts at the importing module; `super::` removes one logical module segment per occurrence and may not remove the owning package root. This same conversion to one absolute `ModulePath` must be shared by macro-import preparation and ordinary import indexing.
- **Rejected alternatives:** Do not retain `extern::` as a compatibility syntax or `--extern` as a compatibility flag; this is an intentional breaking change. Do not keep unprefixed local-relative fallback after top-level lookup fails, because that would make the new rule ambiguous and preserve the old hidden behavior. Do not make `root`, `self`, or `super` hard lexer keywords: they remain contextual words/ordinary identifiers outside the import-anchor positions where the grammar consumes them, while module-identity validation specifically forbids those three spellings.

## Technical Details
- **Initial context boundary:** Start in `compiler/omega-driver` with `docs/language/modules-and-imports.md` and `docs/architecture/module-driver-and-linkage.md`. Open `compiler/omega-parser` / `compiler/omega-hir` only for the changed import source shape, `compiler/omega-analyzer` only for the resolver error contract, and `compiler/omgc` for the CLI registration rename. Use `docs/language/lexical-structure.md`, `docs/language/grammar.md`, `docs/architecture/parsing-and-hir.md`, and `docs/architecture/testing-and-validation.md` for the corresponding grammar/contextual-keyword/test contracts.
- **Affected files/symbols:**
  - `compiler/omega-parser/src/ast/item.rs::ImportRoot` and `compiler/omega-parser/src/parser/item.rs::parse_import`: replace the current `Local / ProjectRoot / Extern` model with explicit top-level/root/self/super semantics; represent repeated leading `super::` as a depth rather than fake path segments.
  - `compiler/omega-parser/src/parser/contextual.rs`: add `super` to the contextual registry; keep `root`, `self`, and `super` usable as ordinary identifiers where import-anchor grammar does not commit them. Extend parser/contextual tests accordingly.
  - `compiler/omega-hir/src/hir.rs::HirImport` and `compiler/omega-hir/src/lower/item.rs`: carry the new import-anchor representation unchanged into HIR; no semantic resolution belongs in HIR.
  - `compiler/omega-driver/src/modules.rs::{macro_env,index_imports,import_absolute_path}`: make one helper convert `(importer logical module path, anchor, source path)` into the absolute path used by both macro and semantic import resolution. Remove `relative_base`, `relative_base_for`, and the `ParsedModule::directory_shaped` state/parameters once no other behavior depends on them.
  - `compiler/omega-driver/src/roots.rs::ModuleRoots`: expose/centralize the facts needed to recognize known top-level package identities and preserve the existing duplicate-identity rule. `root`, `self`, and `super` resolution is always bounded by the importing module's first logical path segment; when analyzing a registered external package, `root::` refers to that package's root, never the consumer package's root.
  - `compiler/omega-driver/src/fs_resolve.rs`: extend module-name policy beyond lexical identifier validity so source-bearing module segments named exactly `root`, `self`, or `super` are rejected. Reuse the same module-name predicate for declared package identities so filesystem-discovered segments, `--name`, inferred package names, and explicit/inferred dependency identities cannot disagree.
  - `compiler/omega-analyzer/src/resolver.rs::ResolveError` and `compiler/omega-analyzer/src/error/render.rs::resolve_error_diagnostic`: remove the source-syntax-specific `UnknownExtern` path and add diagnostics that distinguish an unknown top-level package identity and an invalid `super` traversal above the package root. Update `InvalidModuleName` wording because `root`/`self`/`super` are lexically valid contextual identifiers but invalid module names.
  - `compiler/omgc/src/cli.rs` and `compiler/omgc/src/app.rs`: parse `--import=[<name>:]<dir>` with the same explicit/inferred identity and Windows-drive behavior currently used by `--extern`; update help/errors/tests and reject `--extern` as unknown. Keep driver-internal "extern" terminology where it genuinely means non-emitted/separately compiled ownership rather than performing an unrelated terminology sweep.
  - `bin/test-runner` and `justfile`: register `core`/`std`/`plat` with `--import=...`; rename local runner constants such as `OMGC_EXTERNS` when they describe the CLI surface.
  - Live Omega sources/tests using old resolution (`runtime/core`, `runtime/std`, root `tests/`, and embedded Omega source in `compiler/omega-driver/tests`): external package imports become unprefixed top-level paths; local sibling/descendant imports become explicit `root::`, `self::`, or `super::` paths according to their logical module relationship.
- **Interfaces/invariants:**
  - Unprefixed imports never retry relative to the current module/package. `import std::io::println;` means absolute logical path `std::io::println`, and a missing `std` is a missing top-level package identity, not an invitation to search locally.
  - The local package root and every registered dependency are peers in the top-level namespace; existing duplicate declared-root-identity rejection remains the ambiguity guard.
  - `root::` is package-relative, not invocation-relative. Source inside package `std` resolves `root::fmt` to `std::fmt` even when `std` is being inspected as an imported package during another package's compilation.
  - `self::` starts from the exact logical module being analyzed, independent of whether its filesystem representation is file-shaped or directory-shaped. `super::` removes one logical module segment; chained `super` is allowed only while at least the owning package root remains. `super` at the package root, or any chain that would cross it, is a deterministic compile error.
  - `root`, `self`, and `super` are forbidden only as module/package identities. They are not globally reserved identifiers, so existing contextual-keyword behavior for bindings, fields, parameters, and item names remains intact where grammar permits it.
  - Import aliases still use the imported path's final ordinary segment; visibility/reveal behavior, `core` ambient lookup, package membership, separate-compilation ownership, symbol identity, and import-cycle machinery are unchanged after the absolute path is computed.
  - Macro import environments and post-HIR import indexing must not implement separate path rules; both consume the same anchor-to-absolute-path logic.
- **Out of scope:** FFI `extern` declarations and the separate planned `extern` -> `foreign` language change; re-export semantics; changing `core` prelude behavior; dependency transitivity; package/linkage ownership rules; module filesystem layout beyond removal of its influence on import bases; broad renaming of driver concepts such as externally owned modules; and rewriting historical files under `docs/plan/`.
- **Risks/open questions:** No language-design question remains open. If implementation discovers another consumer of the current import-root representation or `directory_shaped` state beyond the verified parser/HIR/driver sites, preserve the chosen semantics and expand the boundary only for that concrete contract rather than reintroducing relative fallback.

## Implementation Plan
1. **Change the frontend import representation.** In `omega-parser`, add contextual `super`, replace the old import-root variants with an explicit anchor representation, and teach `parse_import` to recognize `root::`, `self::`, and one-or-more leading `super::` prefixes after optional `reveal`; otherwise produce the top-level anchor. Keep the remainder as an ordinary non-empty `Path`, so a final item can still be named `root`, `self`, or `super`. Thread the representation through `HirImport`/HIR lowering without semantic work. Add parser tests for all anchors, chained `super`, ordinary unprefixed paths, and contextual-word non-reservation; assert that old `import extern::...` is no longer accepted as import syntax.
2. **Make absolute import-path construction explicit and shape-independent.** Refactor `omega-driver/src/modules.rs::import_absolute_path` to compute: top-level = source path as-is; root = importing path's first segment + source path; self = full importing module path + source path; super(N) = importing path with N trailing segments removed + source path. Reject N that would remove/cross the first package segment. Use this helper from both `macro_env` and `index_imports`, then delete the old `relative_base*` logic and `ParsedModule::directory_shaped` data that existed solely for implicit-relative imports.
3. **Strengthen top-level/root validation and diagnostics.** Give `ModuleRoots` one query for whether a source-path head is a known top-level identity (local owner or registered dependency). For an unprefixed import whose head is not known, return a dedicated resolution error with guidance that unprefixed imports are top-level and local navigation requires `root::`, `self::`, or `super::`; mention `--import=<name>:<path>` for registering a dependency. Add a dedicated above-root `super` error rather than degrading it into `UnknownModule`. Remove `UnknownExtern` and its `--extern` help.
4. **Reserve the three navigation spellings for module identity only.** Extend the module-name validation used by `fs_resolve::discover_tree` to reject `root`, `self`, and `super` in addition to malformed/reserved lexical identifiers, and apply that same policy to declared local/dependency root identities in `ModuleRoots::new` so direct `Driver` callers cannot bypass it. Keep explicit root-name overrides valid when they relabel a physically awkward directory to a legal logical identity. Update invalid-module diagnostics to say that module names must be valid identifiers and may not use the three import-navigation names.
5. **Rename dependency registration at the CLI boundary.** In `omgc`, replace `--extern=[<name>:]<dir>` with `--import=[<name>:]<dir>` everywhere in parsing, help, errors, and unit tests while retaining the existing basename inference, explicit-name override, repeatability, and Windows drive-letter parsing. Do not accept `--extern` as an alias. Update `bin/test-runner` and `justfile` immediately afterward so normal runtime/test builds use the new flag and the tree remains runnable.
6. **Migrate source imports to the new semantics.** Replace `import extern::std/core/...` in runtime/tests with top-level `import std/core/...`. Audit every currently unprefixed local import in `runtime/core`, `runtime/std`, root conformance packages, and embedded driver test source; make the relationship explicit with `root::`, `self::`, or `super::` rather than mechanically dropping prefixes. In particular, update module-resolution coverage so it exercises `self::` and chained `super::` instead of leaving those constructs untested. Preserve existing visibility and macro-hygiene intent while changing only path anchoring.
7. **Update current documentation.** Rewrite `docs/language/modules-and-imports.md` as the normative rule, including top-level default lookup, the three anchors, chained/above-root `super`, and the module-name exclusion. Update `docs/language/grammar.md` and `docs/language/lexical-structure.md` for contextual `super` and import grammar; update `docs/guide/quick-reference.md` and `docs/guide/compiler-cli.md` examples. Update live architecture/guide/issues references to `--extern`/`extern::` where they describe current behavior (`module-driver-and-linkage.md`, compiler/runtime/platform/symbol docs, console/platform guides, etc.), but leave `docs/plan/` historical records untouched.
8. **Run focused verification, then the full gate.** Fix only regressions caused by the changed import contract; do not fold unrelated module/FFI refactors into this task.

## Testing
- **New/changed cases:**
  - Parser/component tests: unprefixed top-level, `root::`, `self::`, single/chained `super::`, `import reveal` with each applicable anchor, old `extern::` rejection, and `super` remaining contextual outside import-anchor position.
  - Driver component tests: registered dependency resolves via `import lib::...`; a local child no longer resolves via bare `import helper::...`; the same target resolves through `root::`; a directory-shaped module resolves a child through `self::`; nested modules resolve parents/siblings through one and multiple `super`; macro imports follow the same rules; and package-root/over-deep `super` produces the dedicated diagnostic.
  - Module identity tests: source-bearing file/directory segments named `root`, `self`, and `super` are rejected; declared local identities and dependency identities using any of those names are rejected; ordinary contextual identifiers with those spellings remain legal outside module identity.
  - CLI tests in `compiler/omgc/src/cli.rs`: explicit/inferred `--import`, invalid identity, Windows paths, repeatable imports, help text, and explicit rejection of legacy `--extern`.
  - Update `tests/t12_modules_and_imports` to prove the positive language contract with `std::...`, `root::`, `self::`, and chained `super::`. Add focused negative root conformance cases for above-root `super` and at least one reserved module-name failure; component tests should cover all three reserved spellings.
- **Specification trace:** The conformance cases prove the revised `docs/language/modules-and-imports.md` rules: default import paths start in the top-level package namespace; `root`/`self`/`super` select explicit package-relative bases; `super` cannot cross the package root; and the three navigation spellings cannot be module identities. `docs/language/lexical-structure.md` remains the authority that contextual words are not globally reserved.
- **Negative/diagnostic cases:** Assert the intended error, not merely failure, for bare local imports that previously relied on implicit relative lookup, unknown top-level package names, `super` at/above the root, reserved navigation module names, legacy `import extern::...`, and legacy `--extern=...`.
- **Regression coverage:** Run the existing parser contextual-keyword/macro suites and the driver module, macro-hygiene, visibility, entry-point, range/char/conformance suites whose embedded source contains imports. Runtime source compilation is a required regression check because `core`/`std` currently contain both old implicit-relative and `extern::` imports.
- **Commands/target coverage:** Run `cargo test -p omega-parser`, `cargo test -p omega-hir`, `cargo test -p omega-driver`, and `cargo test -p omgc`; build the runtime with the updated `justfile`; run the focused module-resolution conformance cases through `./bin/test-runner`; then run `just test-all`. No backend-specific or hosted-vs-freestanding matrix is required because this change ends at source/package resolution and does not alter MIR, ABI, or codegen.
