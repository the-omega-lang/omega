# Close Remaining Alias Resolution Gaps

## Task Description
- **Deliverable:** Finish the alias cleanup against the current codebase so every behavior already promised by `docs/language/aliases.md`, `modules-and-imports.md`, and `visibility.md` is implemented consistently in every semantic path. The result must close the remaining anchor, lazy-visibility/`reveal`, structural-alias validation, nested generic-obligation, macro-import, overload-re-export, and static-spec import-accounting gaps found in review.
- **Purpose:** Aliases are specified as transparent compile-time naming. The current implementation has the right major architecture (`PathAnchor`, driver-owned alias queries, structural alias expansion, direct alias imports), but several semantic consumers still bypass those abstractions. Those bypasses make equivalent spellings behave differently depending on whether a path is anchored, whether an alias is structural, whether an overload is reached through another module, or whether a generic/static-spec signature is lazy. This task makes those invariants real instead of adding more special cases.
- **Chosen direction:**
  - Keep the existing parser/HIR `PathAnchor` representation; the parser side is already correct. Finish semantic consumption by routing item-like paths through one absolute-path/access result rather than reconstructing paths ad hoc in calls, places, literals, and overload resolution.
  - Collapse lazy item-path visibility state into one representation carrying both the absolute path and whether the later `resolve_item` is allowed to bypass target visibility. This single bit represents an already-authorized capability, whether it came from a validated declared alias target or from `import reveal`; do not lose it between import lookup and lazy item resolution.
  - Split raw alias memoization from **accessor-aware alias lookup**. Semantic use sites must never call the raw query and then infer visibility themselves. Structural alias expansion, forwarding chains, imports, and overload aliases must all pass through the accessor-aware gate.
  - Replace top-level-only alias expansion with one recursive alias-template application operation that normalizes the entire effective type tree and returns every alias-owned bound obligation exactly once, including aliases introduced by another alias RHS/default/bound.
  - Make overload aliases freeze the candidate set visible from the alias declaration site. Store/forward the original candidates; do not create wrappers or redesign overload identity. Analyzer call/value resolution consumes an already-authorized candidate set and never uses `via_alias` heuristics.
  - Keep declaration validation symbolic. Alias-owned generic parameters remain opaque placeholders; validation resolves names/kinds/arity/default availability/visibility and forces nested aliases for cycles without fabricating `ResolvedType`s for placeholders.
- **Rejected alternatives:**
  - Do not add alias-specific `root`/`self`/`super` branches. `PathAnchor` already owns that syntax.
  - Do not keep separate `ItemPath`/`AliasedItemPath` variants plus side-channel `reveal` checks; that is what allowed lazy visibility state to diverge.
  - Do not fix overload re-exporting by skipping candidate visibility whenever `via_alias == true`; that leaks candidates the alias declaration site could not see.
  - Do not patch nested alias bounds by recursively inspecting only the original source spelling; aliases introduced by expansion/defaults would still disappear.
  - Do not redesign generic identity (`$ParamN`) or the overload `ItemKey`/parallel-pipeline architecture in this task. Those are already documented deep debts and require dedicated work.

- **Interfaces/invariants:**
  - `root::`, `self::`, and chained `super::` mean the same thing in imports, types, ordinary value paths, generic calls, overload calls, aggregate literals, static-member paths, alias targets, and macro paths. An explicit anchor is resolved before any “is the head an import?” fallback.
  - An unanchored ordinary path keeps its existing relative/import/lexical behavior. Do not accidentally make all unanchored paths top-level just because imports are top-level-by-default.
  - A lazy imported path carries its authorization to the eventual item query. `import reveal module::HiddenAlias;` must not pass the import gate and then fail later because the reveal bit was discarded.
  - A declared alias is always its own visibility gate. For every alias edge `A -> B`, the module declaring `A` must be allowed to name `B` before `B` is followed. Once a caller passes the outer alias gate, the final target is consumed with the authorization already established by that alias chain; the caller does not re-check the hidden target.
  - Raw alias memoization exists only to build/cache the alias graph and detect cycles. Analyzer semantic resolution uses the accessor-aware alias API.
  - Structural alias use and item-position alias use obey the same arity/default/bound rules. An alias application anywhere in the effective type tree contributes its own obligations; aliases appearing inside defaults, substituted bounds, nested generic arguments, pointers, function types, or another alias RHS cannot disappear.
  - Recursive obligation collection must not duplicate diagnostics merely because an alias parameter is substituted into the RHS more than once. Normalize/check a supplied/defaulted argument once as an argument, then substitute that normalized argument; independently normalize alias applications written in the template body.
  - Declaration-time validation accepts alias-owned generic parameters as opaque placeholders but validates every non-placeholder name, target namespace, alias link, generic arity/default availability, and visibility even when the alias is unused. A bare non-generic alias may forward modules/functions/macros/specs/types; any explicitly-generic alias and any path nested inside structural type syntax is a type/spec position and must not silently accept a function/module/macro/value as a type.
  - `alias render = other::show` where `show` is overloaded forwards **exactly** the candidates visible from `render`'s declaration module. Mixed-visibility groups are valid if at least one candidate is visible; invisible candidates are not included. If no candidate is visible, the alias declaration is `NotVisible`. Alias chains preserve the already-frozen set.
  - Direct non-alias overload lookup keeps ordinary caller-side candidate visibility. `import reveal` bypasses that import/use-site visibility where written. The analyzer never re-filters a frozen overload-alias set against an external caller.
  - Alias/macro forwarding never creates a new function/macro body, symbol, `decl_id`, type identity, vtable identity, MIR node, or codegen entity.
  - Unused-import accounting follows the **effective** signature/type dependency. Static-spec normalization (`f(x: spec A)`) and the aliased equivalent must mark `A`'s import exactly as an explicit generic bound would.
- **Out of scope:**
  - Do not replace synthesized `$ParamN` names with a `GenericParamId`/anonymous-generic identity. Preserve the existing documented entry in `docs/issues/design-debt.md`.
  - Do not redesign `ItemKey`, overload candidate identity, generic overload support, or overloaded static-spec support. Preserve the documented overload-pipeline debt; this task only makes non-generic overload aliases/reveal/visibility correct using the current candidate representation.
  - Do not alter ABI, MIR, mangling, codegen, runtime, or linker behavior. Aliases must still disappear before those phases.
  - Do not perform unrelated module-resolution, generic-system, or formatting refactors.
- **Risks/open questions:** No language decision is open. If a proposed implementation requires changing the normative semantics above, stop and report the conflict rather than choosing a new rule. Deep generic/overload machinery debt must remain documented, not locally worked around.

## Implementation Plan
1. **Unify lazy item-path authorization and make anchored item-path resolution consumable everywhere.**
   - In `compiler/omega-analyzer/src/resolver.rs`, replace the semantic split between `ImportTarget::ItemPath(Vec<Ident>)` and `AliasedItemPath(Vec<Ident>)` with one lazy item-path form carrying both `absolute` and a `bypass_visibility` (or equivalently named) flag. `Item` and `Module` remain distinct.
   - In `compiler/omega-driver/src/resolver.rs::resolve_import_target`, return that lazy form for generic templates and declared aliases that must resolve later; set its bypass flag from the import's `reveal`. Do **not** canonicalize a directly imported declared alias to its hidden target here: preserve the alias path so the eventual alias gate is still meaningful. A normal non-reveal import stores `false`.
   - In `ModuleResolver::resolve_import_alias`'s driver implementation, when the **current module's own declared path alias** has already been validated and forwards an item path, return the final target with `bypass_visibility = true`: this is the already-authorized alias capability, replacing the old `AliasedItemPath` marker.
   - Change `Context::resolve_absolute_item_path` to return a named absolute-path/access result (or the equivalent tuple consistently) and propagate this flag into every eventual `ResolveItemOptions::bypassing_visibility(...)` call. Never discard it when crossing generic/static/literal/place helpers.
   - Finish semantic anchor consumption using the existing `PathAnchor` + `ModuleResolver::resolve_explicit_anchor`; do not change parser/HIR syntax. Update `analysis/paths.rs::generic_prefix_absolute` so an anchored generic prefix is absolutized directly instead of looking up `path.head` as an import. Do the same in `analysis/calls/generic.rs::{resolve_generic_call, resolve_generic_static_call}`, `analysis/places/roots.rs::resolve_place_root`, `analysis/paths.rs::resolve_type_qualified_value`, and the plain/generic branches of `analysis/literals.rs::resolve_literal_target`. `analysis/calls/overload.rs` must also start from the same absolute-path/access result in step 5.
   - Preserve existing unanchored lexical/type fallback: `Type::static_member` and a local variable/type head must still be handled by the current local/type-member logic when no explicit anchor exists. The new common path handling is for item/module resolution, not a replacement for lexical scope.

2. **Introduce one accessor-aware declared-alias lookup and route all semantic alias uses through it.**
   - Keep `Driver::declared_alias(module, name)` as the raw memoized graph query used internally for computing/caching aliases and cycle detection.
   - Extend `ModuleResolver` with a new semantic operation (name it to state the contract, e.g. `resolve_visible_alias`) accepting: accessor module, alias declaration module, alias name, and a visibility-bypass flag. Its driver implementation checks the alias's own visibility unless bypassed, then returns the raw `ResolvedAlias`.
   - Refactor `Driver::forward_alias_path` to use this gate for intermediate aliases instead of open-coding `alias_visibility`; an outer alias declared in module A naming alias B in module C must fail before following B if A cannot see B.
   - Refactor `omega_analyzer::aliases::alias_reference` to carry the access/bypass metadata returned by imports/anchored path resolution and use the accessor-aware alias operation rather than `resolve_declared_alias` directly. This closes direct qualified hidden structural aliases, imported structural aliases, and nested alias chains with one rule.
   - Refactor item/value consumers currently probing `resolve_declared_alias` merely to derive `via_alias` (`analysis/places/roots.rs`, overload code) so they no longer infer authorization from the existence of a raw alias. Those branches should consume the explicit path/overload authorization produced by the resolver instead.
   - Add the direct regression for `import reveal helper::HiddenAlias;` and its structural/generic counterpart. Non-reveal import must reject; reveal import must continue to resolve lazily without re-failing at the alias gate.

3. **Make alias-template application recursive and obligation-complete.**
   - In `compiler/omega-analyzer/src/aliases.rs`, retain `apply_alias_once` as the single binder for one alias template: validate explicit argument count, fill defaults left-to-right, substitute earlier effective arguments into later defaults/bounds, and produce the substituted RHS plus this alias layer's obligations.
   - Replace the current `apply_alias` “while the root is an alias” loop with a recursive normalization over the complete type tree. It must visit pointers/arrays/function params+result/spec conjunction members/generic arguments and alias applications introduced by another alias RHS.
   - Avoid duplicate obligations from substitution: normalize each supplied/defaulted argument once before it is substituted, then normalize alias applications that are syntactically part of the alias template body with alias-owned parameters treated as opaque placeholders. This ensures `alias Duo<T> = Pair<T,T>; Duo<Inner<X>>` checks `Inner<X>` once, while `alias Outer<T> = Pair<Inner<T>,T>; Outer<X>` still collects `Inner<T>`'s obligation from the template body.
   - Recursively normalize alias applications occurring in alias-owned defaults and bounds too. Substitute the final normalized arguments into those bounds before returning `(bound, argument)` obligations.
   - Make `expand_type_alias` and `applied_alias_bounds` thin views of this same recursive result; do not maintain separate expansion and bound traversals. Simplify `Analyzer::check_alias_generic_bounds` so it consumes the canonical obligations and does not need to rediscover nested alias applications by recursively walking only the original source `Type`.
   - Keep path `Origin`/declaration-site provenance intact through substitution. A use-site type argument retains its own origin; template-body paths continue resolving from the alias declaration module.

4. **Finish symbolic declaration-time alias validation instead of validating only name existence.**
   - Rework `Driver::validate_alias_target` in `compiler/omega-driver/src/aliases.rs` into an explicit symbolic type validator. Continue to accept the alias's own generic names as opaque placeholders; do not synthesize `ResolvedType`s for them.
   - Resolve every non-placeholder path with the same anchor/import/declaration-site rules used by semantic alias lookup. In particular, an unqualified name reached through an import must be accepted and validated against the imported absolute path instead of being assumed local. Preserve the alias-specific declaration rule that a fully qualified top-level package path (`main::helper::T`, `std::...`) needs no import: structural alias expansion must carry enough declaration-site binding information that such a target does not validate successfully and then fail later under ordinary use-site `ModuleNotImported` rules. Reuse one driver/resolver alias-target path operation for both declaration validation and later structural expansion rather than teaching `Context::resolve_type` a global top-level exception.
   - Distinguish the two legal declaration modes:
     1. a **non-generic bare `AliasTarget::Path`** may forward any legal alias namespace (module, type/spec, function/overload set, macro, another alias);
     2. an **explicitly generic alias** or any path occurring inside `AliasTarget::Type`/nested type syntax is a type/spec reference. Reject functions, modules, macros, globals, `comp`, gaps, etc. in that position even if the bare alias namespace would allow them.
   - For every `Type::Generic(path,args)` and for a named generic template used with zero explicit arguments, validate generic arity/default availability without materializing a concrete item: ordinary items use `Driver::item_generics`; structural alias templates use their declared `generics`; non-generic targets reject supplied arguments. Recursively validate all explicit/default type syntax. Wrong arity in an unused alias must report at declaration time.
   - In `Type::SpecStatic`, validate every effective member as a spec application/conjunction alias, including generic arity and visibility; a non-spec type/function cannot pass merely because its name exists.
   - Force every nested alias through the raw query while the outer query is in progress so cycles behind pointers/generics/function types/defaults/bounds still produce the existing deterministic alias cycle.
   - Preserve contextual structural forms that are intentionally meaningful only after expansion (`alias AB = spec A+B`, aliases involving `str`, pointer forms). Validation proves the referenced names/kinds/template shapes are legal; it must not prematurely impose a use-site context that would make a transparent alias less expressive than the literal type syntax it stands for.

5. **Replace overload `via_alias` heuristics with an alias-aware candidate-set query that freezes declaration-site visibility.**
   - Extend `ResolvedAlias` with an overload-set form that stores the target overload group's absolute path and the **already filtered original candidates** (or stable candidate identifiers sufficient to reconstruct that exact set). This is not a new function identity; every candidate keeps its original `decl_id`/signature.
   - In `Driver::forward_alias_path`, detect `ModuleIndex::overloads[name]` before treating the name as an ordinary single item. Obtain the raw current candidates from `function_overload_signatures`, filter each candidate using `visibility_allows(candidate.visibility, target_module, alias_declaration_module)`, and store exactly the visible subset. If the raw group exists but the subset is empty, return `NotVisible`. A mixed exposed/hidden group therefore produces a valid alias containing only the candidates the aliasing module could actually name.
   - Alias-to-alias chains that end in an overload set must forward the already-frozen subset after the intermediate alias visibility gate; do not reopen the raw target group and accidentally add candidates back.
   - Add a new `ModuleResolver` overload lookup operation taking accessor, written/absolute binding, and bypass state and returning the correct `OverloadCandidates`: plain direct/imported overloads are filtered against the accessor (unless `reveal` bypasses); a declared overload alias is gated once through the accessor-aware alias API and then returns its frozen set unchanged.
   - Update `analysis/calls/overload.rs::{resolve_bare_overload_candidates, resolve_overloaded_call}` and `analysis/paths.rs::resolve_qualified_value` / `analysis/places/roots.rs::resolve_bare_overload_root` to use that operation. Remove `via_alias`, `import_reveal`, raw `function_overload_signatures` + local filtering, and `raw_import_absolute_path` uses that exist only to reconstruct this authorization in the analyzer.
   - Preserve the deep limitation that overload candidates themselves cannot be generic/static-spec-generic. Do not change `ensure_overload_signature`, overload cache keys, or `ItemKey` as part of this step.

6. **Make bare imported macro aliases use ordinary declaration-site import semantics.**
   - In `compiler/omega-driver/src/modules.rs::raw_macro_target`, keep local macro lookup first for an unqualified target. If no local definition exists, look for an import whose bound name matches the target and resolve that import with `import_absolute_path`; then fetch/gate the target macro from its defining module.
   - Honor the import's `reveal` when deciding whether the imported macro binding itself is usable. Align `macro_env`'s ordinary imported-macro insertion with the same rule so `import reveal ...` cannot work differently depending on whether the imported macro is invoked directly or immediately aliased.
   - After the imported binding is obtained, an alias of that macro still receives the alias declaration's own visibility and the original macro definition module/body for hygiene. An exposed macro alias must continue to run dependency-leak checks using the alias visibility.
   - Keep the existing anchored/qualified macro target path behavior and per-link alias visibility gates; this step only closes the missing bare imported-macro branch and makes `reveal` consistent.

7. **Make unused-import dependency accounting consume normalized function signatures and canonical alias dependencies.**
   - In `compiler/omega-driver/src/compile/signatures.rs::collect_signatures`, stop collecting raw `f.generics` for function definitions. For each `HirItem::FunctionDefinition`, obtain `Driver::normalized_function(path,f)` and pass its normalized generics to `mark_bound_type_imports`; other generic item kinds may keep their existing declared generic list.
   - This specifically ensures a source function such as `f(x: spec ImportedSpec)` marks the import used even though static-spec normalization turns the function into a lazy generic template that is skipped by the normal eager item sweep. The alias spelling (`alias S = spec ImportedSpec; f(x:S)`) must hit the same normalized path.
   - Keep `mark_type_import_dependencies` responsible for traversing alias RHS/bounds/defaults in the **alias declaration module**, and the use-site import responsible only for the imported alias binding itself. Update it to consume the unified lazy item-path representation from step 1 and accessor-aware alias resolution from step 2; do not duplicate alias expansion rules here.
   - Ensure import-accounting traversal is cycle-safe by alias declaration identity and does not mark an inaccessible/invalid alias dependency as successfully used merely because validation later fails.

8. **Update architecture docs to describe the final interfaces; preserve only the two intentional deep debts.**
   - `docs/language/*.md` already describe the desired language behavior. Do not add caveats for the bugs being fixed. Only edit them if a current sentence becomes inaccurate because an internal term changed; semantics stay unchanged.
   - Update `docs/architecture/semantic-analysis.md` so its “canonical alias application” section explicitly matches the recursive whole-type operation and accessor-aware structural alias lookup actually implemented.
   - Update `docs/architecture/module-driver-and-linkage.md` for the unified lazy item-path authorization, raw-vs-accessor-aware alias query boundary, declaration-time symbolic validation, and frozen overload alias candidate set. Remove references to `AliasedItemPath`/old `via_alias` behavior if those names disappear.
   - Keep `docs/issues/design-debt.md` entries for (a) fabricated `$ParamN` generic identity and (b) the parallel overload/`ItemKey` architecture including overloaded static-spec/generic candidates. Verify this task did not introduce a local workaround that obscures either debt.

9. **Run focused cleanup only after every regression passes.**
   - Remove now-dead `via_alias`, `AliasedItemPath`, and analyzer-side raw visibility reconstruction paths. Remove `raw_import_absolute_path` from `ModuleResolver` if it has no remaining legitimate caller after overload resolution is centralized; do not keep an API whose only purpose was the old heuristic.
   - Keep comments only where they state the non-obvious capability/visibility invariant. Update names rather than preserving comments that describe superseded variants.
   - Run formatter only on the touched workspace in the normal way (`cargo fmt --all`); do not reopen unrelated formatting/refactor work.
