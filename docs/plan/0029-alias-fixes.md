# Finish Alias Semantics and Path Resolution Cleanup

## Task Description
- **Deliverable:** make aliases fully transparent and consistently usable across paths, imports, generics/spec bounds, macros, overloads, visibility, and diagnostics; remove the implementation-only restrictions and alias-specific correctness gaps found after the initial alias implementation; leave only genuinely foundational generic/overload redesigns as explicitly documented debt.
- **Purpose:** Omega's `alias` promises compile-time name indirection with no semantic identity of its own. Literal spelling and aliased spelling must therefore behave the same, and `root::` / `self::` / `super::` must be ordinary path semantics rather than an import-only exception. Fix the current cases where aliases leak through validation, visibility, import accounting, generic bounds, or overload selection.
- **Chosen direction:** generalize explicit path anchors into `Path` itself; centralize alias application so one operation binds effective generic arguments, expands alias chains, and carries bound obligations; make alias lookup accessor-aware at visibility boundaries; route imports, macros, overloads, and import-usage accounting through those canonical semantics instead of adding per-feature alias patches.
- **Rejected alternatives:** do not special-case `root`/`self`/`super` in alias parsing; do not validate generic aliases by inventing fake concrete types; do not keep separate default/bound logic for type-position versus item-position aliases; do not preserve misleading `ImportTarget::GenericItem` naming merely to avoid localized churn; do not solve the deep `$ParamN`/generic-identity or general overload query-key problems inside this task.

## Technical Details
- **Initial context boundary:** start in `compiler/omega-parser` (`ast/identifier.rs`, `ast/item.rs`, `parser/mod.rs`, `parser/item.rs`, `parser/expression.rs`), `compiler/omega-hir` (`hir.rs`, `lower/item.rs`), `compiler/omega-analyzer` (`aliases.rs`, `resolver.rs`, `analysis/mod.rs`, `analysis/paths.rs`, `analysis/calls/overload.rs`), and `compiler/omega-driver` (`aliases.rs`, `resolver.rs`, `modules.rs`, `conformances/registration.rs`, `items/resolution.rs`). Use `docs/language/aliases.md`, `modules-and-imports.md`, `visibility.md`, `generics.md`, `specs-and-conformance.md`, `macros.md`, and `grammar.md` as normative context; architecture context is `parsing-and-hir.md`, `semantic-analysis.md`, `module-driver-and-linkage.md`, and `testing-and-validation.md`.
- **Affected files/symbols:**
  - `omega_parser::ast::identifier::Path` and `omega_parser::ast::item::{ImportStmt, ImportRoot}`: explicit `root::`, `self::`, and chained `super::` currently live outside ordinary paths. Move explicit anchoring into `Path`; imports should no longer own a separate anchor representation. Update every synthetic `Path` constructor and preserve origin/hygiene metadata.
  - `parser::{parse_path, parse_expr_path}` and `parser::item::parse_import`: share leading-anchor parsing. `root`, `self`, and `super` remain contextual: only a leading anchored form followed by `::` is navigation; ordinary identifier positions remain ordinary identifiers where otherwise legal.
  - `omega_driver::modules::import_absolute_path` and other path absolutization/lookup sites: resolve a `Path`'s explicit anchor relative to the path's semantic resolution module. For macro-expanded paths this remains the macro-origin module; for aliases it is the alias declaration module. An unanchored import remains top-level-by-default, while an unanchored ordinary path keeps its existing lookup rules. `super` may not cross the owning package root and keeps the dedicated diagnostic.
  - `omega_driver::aliases::{declared_alias, compute_alias, force_nested_aliases, validate_aliases, forward_alias_path}`: declaration validation must fully validate structural alias targets even when never used; alias chains must check every intermediate alias's visibility from the accessor that names it before following the chain.
  - `omega_analyzer::aliases::{expand_type_alias_once, expand_type_alias, applied_alias_bounds, substitute_type_params}`: replace divergent expansion/bound helpers with one alias-application result that binds all effective raw arguments (explicit plus defaults), substitutes the RHS, substitutes alias-owned bounds, and accumulates obligations through every alias layer. Imported and qualified structural aliases must use the same operation.
  - `omega_driver::resolver::{resolve_alias_type, resolve_import_target}` and `omega_driver::items::resolution` generic-default helpers: reuse one default/arity rule so alias templates honor defaults in ordinary type positions and in item/static-member/aggregate-construction positions. Direct imports of aliases must resolve the alias name as a declaration binding rather than assuming it exists in `ModuleIndex::items`.
  - `omega_analyzer::resolver::ImportTarget::GenericItem`: rename the lazy unresolved item-path carrier to a truthful name such as `ItemPath` and update all analyzer/driver consumers. Preserve `reveal` semantics when an imported alias/item remains lazily resolved; do not erase the import's visibility bypass while converting representations.
  - `omega_driver::conformances::registration::mark_bound_type_imports` and signature/import-usage preparation: replace the raw-HIR-only walk with alias-aware type dependency accounting. Imports consumed through structural alias RHSs, alias-expanded conjunction bounds, defaults/bounds, or static-spec normalization count exactly as if the final type/spec spelling had appeared directly.
  - `omega_driver::modules::{module_macros, bind_macro_aliases, raw_macro_target}`: when an alias names a macro, check the target macro binding's visibility from the alias declaration module before accepting it. Keep the original macro definition module/body for hygiene and the alias visibility as the effective re-export visibility.
  - `ModuleResolver::function_overload_signatures`, `omega_driver::resolver`, `omega_analyzer::analysis::calls::overload`, and overload-as-value lookup in `analysis/paths.rs`: make overload lookup aware of the written alias and accessor. An alias first gates the caller by alias visibility, then freezes/forwards the candidate set visible from the alias declaration site; the caller must not re-check the underlying candidates' original visibility. Direct non-alias qualified calls and `reveal` retain their existing rules.
  - `omega_analyzer::analysis::paths::resolve_qualified_value`: preserve a specific `NotVisible` error discovered while probing `module::Type::member`; fall back to `UnknownModule` only when the alternate interpretation genuinely does not resolve.
  - `docs/issues/design-debt.md` / `docs/issues/language-limitations.md`: explicitly record the two deep issues left for dedicated tasks: (1) static-spec anonymous generics are represented with fabricated impossible-source `Ident("$ParamN")` names instead of semantic generic-parameter IDs/origin metadata; (2) overloaded static-spec/generic functions remain blocked by the parallel overload candidate/query-key pipeline (`ensure_overload_signature` analyzes candidates without a generic substitution). Cross-reference the existing overload design-debt entry rather than proposing another local workaround.
- **Interfaces/invariants:**
  - An alias never gains checked/MIR/layout/vtable/mangling/symbol identity; all successful resolution ends at the canonical target identity.
  - Every alias declaration is validated even if unused. Structural templates may contain alias-owned generic parameters, but every other referenced type/spec/path/declaration must be resolvable and legal at the declaration site.
  - Every alias in a cross-module chain is its own visibility gate. Once a valid alias has been selected by a caller, its target is accessed with the alias declaration module's rights; the caller does not re-satisfy the underlying target visibility.
  - A macro alias follows exactly the same capability-transfer rule while retaining definition-site hygiene.
  - A function overload alias forwards the complete candidate set visible at alias declaration, not a caller-dependent subset and not candidates invisible to the alias declaration.
  - Alias generic defaults and bounds are semantic obligations of the alias application. Defaults are included in arity/binding, parameter references inside bounds are substituted, and alias chains cannot discard obligations.
  - Explicit path anchors are syntax/semantics of `Path`, not of imports or aliases. They work wherever a path is legal, including nested type syntax such as `*self::T`, generic arguments, function types, expressions, imports, aliases, and macros.
  - `Path` equality/hash must distinguish semantically different explicit anchors while continuing to exclude source `Origin` from semantic path equality where it is excluded today.
  - Import-use diagnostics observe final alias-transparent dependencies; a truly unused import still warns.
  - Deterministic cycle/visibility/diagnostic ordering must not regress.
- **Out of scope:** do not replace generic parameter identity with `GenericParamId`/anonymous generic nodes in this task; leave `$ParamN` as collision-safe internal compatibility representation and document the debt. Do not redesign `ItemKey`, candidate identity, or the parallel overload item pipeline to support generic/static-spec overloads generally; document that limitation. Do not redesign module/item paths into new interned typed IDs, add local/value aliases, create alias wrapper symbols, or change alias transparency/ABI semantics.
- **Risks/open questions:** no user decision is currently required. If preserving imported `reveal` semantics while making aliases directly importable exposes an undocumented contradiction in existing import behavior, stop and surface the exact contradiction rather than silently choosing new language semantics. Otherwise preserve the documented visibility model.

## Implementation Plan
1. **Make explicit module navigation part of ordinary paths.** Add an optional explicit anchor/root field to `omega_parser::Path` for package root, current module, and parent depth; remove `ImportRoot` from `ImportStmt`/HIR. Refactor the parser so ordinary path parsing recognizes leading `root::`, `self::`, and chained `super::`, while an unanchored import is still top-level-by-default. Update HIR lowering, parser prelude exports, path equality/hash, all synthetic `Path` constructors, and alias origin-retagging. Centralize driver absolutization so imports, aliases, normal semantic lookup, and pre-expansion macro lookup consume the same anchored path meaning instead of reimplementing it.
2. **Create one canonical alias-template application operation.** In `omega-analyzer::aliases`, bind the full effective argument list using explicit arguments plus defaults, validate arity once, build the alias-parameter substitution, substitute the RHS and every alias-owned bound, and return both the expanded type and accumulated `(argument, bound)` obligations. Repeated expansion must accumulate obligations from each alias in a chain and recurse through nested type arguments. Replace `applied_alias_bounds`/ad-hoc expansion behavior with this operation and reuse the existing generic-default policy rather than maintaining a second rule.
3. **Make structural alias declaration validation real and non-materializing.** Replace/narrow `force_nested_aliases` so `Driver::validate_aliases` symbolically validates every alias target at declaration time, including unused aliases and generic templates. Alias-owned parameters are legal placeholders; every other type/spec/path must resolve, generic applications/defaults/bounds must be structurally valid, forbidden value/gap targets must reject, nested aliases must be forced for cycle detection, and target visibility must be checked from the declaration site. Do not fabricate concrete `ResolvedType` cells for symbolic generic parameters merely to reuse use-site resolution.
4. **Unify alias lookup through imports and item-position consumers.** Teach `resolve_import_target` to recognize a declared alias before assuming an indexed concrete item, so `import module::Alias;` works for legal exposed aliases. Make `omega_analyzer::aliases::alias_reference` resolve imported/qualified alias bindings through ordinary path/import resolution rather than looking only in the current module. Update `resolve_alias_type` and aggregate/static/generic-call paths to consume the canonical alias application from step 2, including defaulted alias parameters. Rename `ImportTarget::GenericItem` to `ItemPath` (or an equally precise final name) and update all consumers; retain import `reveal` metadata wherever lazy resolution requires it.
5. **Enforce alias visibility at every forwarding boundary.** Split raw memoized alias lookup from accessor-aware alias lookup. `forward_alias_path` must check an intermediate alias's visibility before following it, including cross-module chains, while callers of an already-valid outer alias continue to use that outer alias's declaration rights for its target. Apply the same rule to direct imports of aliases. Add focused diagnostics at the alias declaration/import site instead of allowing a hidden intermediate binding to disappear into the final target.
6. **Make macro alias lookup obey the same visibility model.** In the raw macro environment/binding pass, resolve anchored paths through the shared path machinery and reject a macro target not visible from the alias declaration module. For alias chains, use each module macro binding's effective visibility as the next gate. Continue carrying the original macro body's defining module for hygiene and use the outer alias visibility for downstream dependency-leak checks.
7. **Make overload aliases true re-exports without redesigning overload identity.** Introduce an alias-aware overload-candidate query/API at the driver/analyzer seam: resolve the written binding, check the alias/import visibility/reveal gate, collect the target overload group, and filter candidates using the alias declaration site's rights. Use that same result for call overload resolution and overload-as-value resolution. Never filter the already-forwarded candidate set again against the external caller. Keep direct non-alias overload lookup behavior intact. Do not attempt the deeper generic/static-spec overload pipeline redesign in this step.
8. **Replace raw bound import marking with alias-aware dependency accounting.** Give driver signature/conformance preparation a single traversal that observes alias applications/expansion and their declaration-site origins and marks imports actually consumed by effective types/spec bounds/defaults. Use it for generic bounds, static-spec normalized bounds where applicable, and structural alias declaration validation/RHS dependencies. Ensure a module importing an alias directly marks that alias import as used while imports referenced only inside the alias declaration are accounted in the alias's declaration module.
9. **Fix the adjacent visibility diagnostic.** In `resolve_qualified_value`, distinguish “the prefix is not a module but resolves to an inaccessible type/item” from “nothing resolves”; propagate `NotVisible` (and other more specific relevant errors) rather than swallowing it into `UnknownModule`. Keep the type/static-member fallback itself unchanged.
10. **Bring documentation to the implemented contract and record only deep debt.** Update `docs/language/aliases.md` to remove the anchor restriction and state that aliases use ordinary anchored paths; update `grammar.md` and `modules-and-imports.md` so anchors are general path syntax while bare imports remain top-level. Update alias/generic/spec/macro/visibility text for direct alias imports, generic obligations, and deliberate re-export behavior. Remove stale “Omega has no re-export” statements from `docs/issues/language-limitations.md` and `docs/issues/known-issues.md`; keep ordinary imports non-transitive but describe aliases as the explicit re-export mechanism. Update `parsing-and-hir.md`, `semantic-analysis.md`, and `module-driver-and-linkage.md` for path-owned anchors and canonical alias application/visibility. Add the `$ParamN` semantic-identity debt and the overloaded static-spec manifestation to the appropriate `docs/issues/` entries with the dedicated-task boundary stated above.
11. **Finish with mechanical repository formatting cleanup.** After semantic/doc changes are stable, run workspace `cargo fmt --all` and accept formatter-only changes needed to make `cargo fmt --all -- --check` clean. Do not combine this with unrelated manual refactors or behavior changes; formatting is the only repository-wide cleanup authorized by this task.
