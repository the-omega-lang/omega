# Add `hidden` as an explicit, parseable visibility keyword

## Task Description

- **Deliverable:** `hidden` becomes a real contextual keyword usable anywhere `exposed`/`shared` are currently accepted as a visibility modifier (top-level items, struct/union fields and methods, enum header fields, enum/primitive methods). Additionally, `spec` member declarations — which today accept **no** visibility modifier at all and always inherit the spec's own visibility — gain the ability to take an explicit modifier that must be `<=` the spec's own visibility, defaulting to the spec's visibility when omitted (unchanged from today). Writing `hidden` in any context where it changes nothing (i.e. it equals what the default would have been anyway) produces a new suppressible warning.
- **Purpose:** `hidden` is already the implicit default almost everywhere, but there is currently no token for it, so it cannot be *written*. That is a problem specifically for spec bodies: a spec's default-implementation methods (bodies with a default impl) need to call implementation-detail helper methods declared in the same spec without being forced to expose those helpers at the spec's own visibility. There is currently no way to declare a spec member less visible than the spec itself.
- **Chosen direction:**
  - `hidden` is added to the same contextual-keyword mechanism as `exposed`/`shared` (`compiler/omega-parser/src/parser/contextual.rs`, `ALL` slice) and to `parse_optional_visibility` (`compiler/omega-parser/src/parser/item.rs:191-214`). Writing it explicitly takes the existing `ParsedVisibility::Explicit { visibility: Visibility::Hidden, span }` arm (mirroring `EXPOSED`/`SHARED`); omitting any modifier keeps hitting the existing `ParsedVisibility::Hidden` (no-span) fallback arm. `ParsedVisibility` already distinguishes "written" from "omitted" via `explicit_span()` — no new type is needed to know a modifier was explicitly written.
  - Spec member declarations (`parse_spec_function`, `compiler/omega-parser/src/parser/item/definitions.rs:222-261`, used by both `parse_spec_def` and `parse_gap_def`) currently take zero visibility syntax. `parse_spec_def`'s loop (`definitions.rs:203-209`) already has the enclosing spec's own `visibility: Visibility` in scope before it parses members, so the "member visibility must not exceed spec visibility" rule is a purely syntactic, parse-time check — no analyzer/semantic pass is needed for it. `parse_gap_def`'s loop must keep rejecting any modifier on gap functions exactly as today (gaps are out of scope for this feature — see Out of scope). Because both loops call the same `parse_spec_function` helper, give it an explicit policy parameter (mirroring the existing `MemberVisibility::{Allowed, InheritedFromSpec}` split already used by `parse_member_functions`) rather than special-casing inside one shared function body.
  - The "redundant `hidden`" warning is implemented as a new `omega-analyzer` `AnalysisWarningKind` variant, not a new parser-level warning mechanism, even though the redundancy fact is knowable at parse time. Rationale: `omega-analyzer` already owns the only warning/suppression pipeline in the compiler (`@suppress(name)`, resolved from annotations during analysis — see `compiler/omega-analyzer/src/error/warning.rs` and `analysis/mod.rs:277-292`); the parser has no warning severity or suppression concept at all today. Building a second, parser-native warning pathway for one check would duplicate that mechanism and make this one warning uniquely unsuppressible. Instead, thread the fact "an explicit `hidden` was written, and here is its span" from parse time into HIR as a small sibling field next to each existing `pub visibility: Visibility` field, and let the analyzer compare it against the locally-known default at the same points it already visits these nodes for other per-declaration warnings (e.g. `UnusedField`, `UnusedVariable`).
- **Rejected alternatives:**
  - A parser-native warning pathway for just this check — rejected as a duplicate warning mechanism (see above); would also leave this warning unsuppressible unlike every other one.
  - Making spec-member visibility a hard floor equal to the spec's visibility with `hidden` as a single special-cased exception — rejected in favor of a general ceiling (`member visibility <= spec visibility`, any of `hidden`/`shared`/`exposed` allowed when they satisfy it) so `hidden` behaves like an ordinary modifier there too, per the user's own framing ("hidden should work as any other visibility modifier currently does"), and so an `exposed spec` can symmetrically declare `shared` or `hidden` helper members. This is a generalization beyond the user's single worked example (which only showed `hidden`); flag it in the report so the user can confirm or narrow it.

## Technical Details

- **Initial context boundary:** `compiler/omega-parser` (lexer keyword table, AST, spec/member parsing), `compiler/omega-hir` (HIR node definitions + lowering for the touched node kinds), `compiler/omega-analyzer` (spec flattening, visibility checks, the warning framework), plus `docs/language/visibility.md` (normative chapter for this exact keyword) and `docs/guide/quick-reference.md`.
- **Affected files/symbols:**
  - `compiler/omega-parser/src/parser/contextual.rs`: add `pub const HIDDEN: &str = "hidden";` to the `ALL` slice.
  - `compiler/omega-parser/src/parser/item.rs`: extend `parse_optional_visibility` (lines 191-214) with a `HIDDEN` arm producing `ParsedVisibility::Explicit { visibility: Visibility::Hidden, span }`.
  - `compiler/omega-parser/src/parser/item/definitions.rs`:
    - `field_follows` (lines 120-132): its field-vs-modifier disambiguation currently special-cases `EXPOSED`/`SHARED`; extend to `HIDDEN` too (a field literally named `hidden` must still parse).
    - `parse_spec_function` (lines 222-261) and its two callers (`parse_spec_def` loop at 203-209, `parse_gap_def` loop at ~277-305): thread an explicit visibility policy through as described in Chosen direction. Add `pub visibility: Visibility` to `SpecFunctionStmt` (`compiler/omega-parser/src/ast/item.rs:102-112`); `GapStmt` functions keep `Visibility::Hidden`/unused-here since gaps reject modifiers.
    - New `ParseErrorKind` (e.g. `SpecMethodVisibilityExceedsSpec`) in `compiler/omega-parser/src/diagnostics.rs`, reported immediately in `parse_spec_def`'s member loop when an explicit member modifier is greater (by `Visibility`'s derived `Ord`) than the spec's own visibility. Model the message/help on the existing `ConformMethodVisibility` entry (`diagnostics.rs:94-96`) and `VisibilityNotAllowedHere`/`GapOrGlueVisibility` nearby.
  - `compiler/omega-parser/src/ast/visibility.rs`: no change needed — `Visibility::Hidden`'s `Display` impl already renders `"hidden"`.
  - `compiler/omega-hir/src/hir.rs`: add `pub visibility: Visibility` to `HirSpecFunction` (~line 221; it has none today). Add a sibling `pub explicit_hidden_span: Option<Span>` next to the existing `pub visibility: Visibility` field on: `HirField` (:116), `HirFunctionDef` (:127), `HirStructDef` (:164), `HirUnionDef` (:177), `HirEnumDef` (:189), `HirExternDeclaration` (:95), `HirSpecDef` (:211, the spec item's own visibility), and the new `HirSpecFunction.visibility`.
  - `compiler/omega-hir/src/lower/item.rs`: `lower_spec_function` (~362) and the lowering sites for the other node kinds above: populate the new fields from the corresponding AST `ParsedVisibility`/stored visibility.
  - `compiler/omega-analyzer/src/resolved_type.rs`: `RawSpecFunctionSig` (line 200) needs a `visibility: Visibility` field; `ResolvedSpecType.functions` construction site (`compiler/omega-analyzer/src/analysis/specs.rs` ~line 320) populates it from `HirSpecFunction.visibility` instead of always defaulting.
  - `compiler/omega-analyzer/src/analysis/specs.rs`: `flatten_spec_into` (~line 547-604) currently assigns `visibility: spec_visibility` uniformly to every `FlattenedSpecFn` it pushes (~line 604); change to use the per-function `RawSpecFunctionSig.visibility` captured above.
  - `compiler/omega-analyzer/src/error/warning.rs`: new `AnalysisWarningKind::RedundantHiddenModifier` (or similar name), following the `RedundantLayoutAnnotation`/`UnnecessaryMut` pattern exactly: `name()` entry (e.g. `"redundant_hidden_modifier"`), `Display` text, and a `to_diagnostic()` render arm with a `with_help` pointing at removing the modifier.
  - `compiler/omega-analyzer/src/analysis/mod.rs` and wherever the analyzer already visits `HirField`/`HirFunctionDef`/top-level `Hir*Def`/`HirSpecFunction` nodes for other per-declaration warnings (search for the `UnusedField`/`UnusedVariable`/`RedundantLayoutAnnotation` emission sites as the pattern to mirror): call `self.warn(...)` when `explicit_hidden_span.is_some()` and the value equals the locally-known default (unconditionally `Hidden` for every node kind except `HirSpecFunction`, where the default is the enclosing spec's own visibility — already known wherever `HirSpecFunction`s are visited alongside their owning `HirSpecDef`).
- **Interfaces/invariants:**
  - `Visibility`'s existing `Ord` (`Hidden < Shared < Exposed`) is the correctness basis for the spec-member ceiling check — do not introduce a parallel comparison.
  - A spec's default-implementation body calling a same-spec `hidden` sibling method via `Self::` must keep working through the *existing* general same-item/same-module access rule once `FlattenedSpecFn.visibility` correctly carries the per-function value — this requires no new access-control code, only that the value is no longer forced to `spec_visibility` uniformly. Confirm this with the conformance test rather than adding a bespoke check.
  - Gaps/glues and `conform` methods keep rejecting any visibility modifier exactly as today (`reject_gap_glue_visibility`, `ConformMethodVisibility`) — unaffected by this change.
- **Out of scope:**
  - `gap` function declarations do not gain visibility-modifier syntax (they remain implicitly `Exposed`-contract, no modifier accepted).
  - No change to `conform` method visibility rules.
  - No generalization of the redundancy warning to `exposed`/`shared` (e.g. "unnecessary explicit `shared` on an already-`shared` spec member") — only literal `hidden` redundancy, per the user's request.
  - `docs/plan/` untouched.
- **Risks/open questions:** none blocking — the one generalization decision made above (general ceiling for any modifier on spec members, not just `hidden`) is flagged for the user in the final report rather than gated on it, since it follows directly from the user's own stated rationale and the existing `Ord`-based visibility model. If the developer finds a place where `HirSpecFunction`/spec flattening is consumed in a way that assumes uniform per-spec visibility (e.g. dynamic-dispatch vtable generation keyed by spec, not by member) and per-member visibility would break an existing invariant there, stop and escalate rather than forcing it through.

## Implementation Plan

1. Add the `HIDDEN` contextual keyword and its `parse_optional_visibility` arm; update `field_follows`. Build (`cargo build -p omega-parser`) — this alone makes `hidden` parse anywhere `exposed`/`shared` already do, with `Visibility::Hidden` as the resulting value (no observable behavior change yet, since it already defaulted to `Hidden`).
2. Add `SpecFunctionStmt.visibility`, thread the ceiling-checked optional modifier through `parse_spec_def`'s member loop and `parse_spec_function`, keep `parse_gap_def` rejecting modifiers, add the new `ParseErrorKind`. Build `omega-parser`; fix any compile errors in its own test/call sites.
3. Add `HirSpecFunction.visibility` and lower it; add `explicit_hidden_span: Option<Span>` to the HIR node kinds listed above and populate them during lowering. Build `omega-hir`.
4. Add `RawSpecFunctionSig.visibility`, populate it from HIR, and make `flatten_spec_into` use per-function visibility instead of `spec_visibility` uniformly. Build `omega-analyzer`; run its existing spec/visibility unit tests and fix fallout.
5. Add `AnalysisWarningKind::RedundantHiddenModifier` and emit it at the relevant HIR-visitation sites (top-level items, fields, methods, spec members). Run `cargo test --workspace`.
6. Update docs: `docs/language/visibility.md` (add `hidden` as an explicit keyword alongside the existing `shared`/`exposed` sections; document the spec-member ceiling rule with an example close to the user's), `docs/language/lexical-structure.md` (contextual keyword list), `docs/language/grammar.md` (`visibility = "exposed" | "shared" | "hidden" ;`), `docs/guide/quick-reference.md` (visibility example block), and `docs/language/specs-and-conformance.md` if it documents spec member visibility inheritance (check before editing; skip if it doesn't cover the point).

## Testing

- **New/changed cases:**
  - Root conformance case (extend `tests/t13_visibility/` rather than adding a new directory, since it is already the canonical visibility suite — read `t13_visibility.omg`/`child.omg`/`expected.stdout` first): a spec with a `shared` (or `exposed`) declared visibility, one member with no modifier (inherits spec visibility), one member explicitly `hidden`, and a default-implementation method calling the `hidden` sibling via `Self::` — prove it compiles and runs, and that the `hidden` member is genuinely inaccessible from outside the package the same way an ordinary `hidden` struct field/method already is (t13 already has that assertion shape for other members — mirror it).
  - Negative/diagnostic case (new or extended `tests/<case>/`, or a targeted `omega-parser`/`omega-driver` component test if it doesn't need full conformance): a spec member modifier exceeding the spec's own visibility (e.g. `exposed` member in a `shared spec`) produces the new `SpecMethodVisibilityExceedsSpec` diagnostic — assert on `expected.stderr` exact text, not just failure.
  - Redundant-`hidden` warning: a component-level `omega-analyzer` test (mirror an existing `RedundantLayoutAnnotation`/`UnnecessaryMut` test in that crate's test suite) asserting the warning fires for `hidden` on an ordinary struct field and does *not* fire for `hidden` used to legitimately loosen a spec member below the spec's own visibility.
- **Specification trace:** `docs/language/visibility.md`'s updated `hidden` section and the spec-member ceiling rule are what `tests/t13_visibility` must demonstrate end-to-end.
- **Regression coverage:** `tests/t13_visibility` (primary), `tests/t18_macros` and `tests/t19_foreign_function_interface` (both touch visibility modifiers on unrelated declarations — confirm the `HIDDEN` keyword addition doesn't shift any contextual-keyword disambiguation there), `tests/t01_lexical_structure` (confirm `hidden` still lexes as an ordinary identifier outside a visibility position, matching the existing proof pattern for `exposed`/`shared`/etc. in that file).
- **Commands/target coverage:** `cargo build --workspace`, `cargo test --workspace` (focus on `omega-parser`, `omega-hir`, `omega-analyzer`, `omega-driver`), then `just test-all` as the final full gate.
